# 評価に使うネットワーク（学習した補正）

探索 AI が局面に付ける点数は、手で作った評価（`eval.rs`）と、学習した補正（`data/value-net.json`）の和。
2026-10-31 からの既定の補正（relearn8）は手で作った評価を 0 にして学んだもの（`--base zero`）で、点数は補正だけで付く（下の「評価の式」）。
この文書は、補正のネットワークの形・入力・出力・学習のしかた・使われ方をまとめる。
試したことの経緯と数字は [ai-notes.md](ai-notes.md) と [ai-notes/](ai-notes/) にある（文中の「」は ai-notes.md の節の索引から辿れる節の名前）。

2026-10-31 時点の既定の補正 **relearn8**（2026-10-31 採用）について書く。既定の補正を学び直したら、この文書の数字（a・c・重みの数・経緯の表）も直す。

## 早見

| 項目 | 中身 |
| --- | --- |
| 何を当てるか | 局面から、視点のプレイヤーが勝つ確率。探索の点数には、手で作った評価に足す補正として入る |
| 形 | 全結合の 3 層。入力 3506 → 隠れ層 256（ReLU）→ 隠れ層 32（ReLU）→ 出力 1。重みとバイアスは合わせて 906,051 個 |
| 入力 | 視点のプレイヤーに見える情報だけ。カード・クレストごとの枚数など（14 種類 × 248）と数値 34 個。1 局面で 0 でない入力は平均 35 個ほど |
| 出力 | 勝つ確率のロジットへの補正 z。勝つ確率 = σ(a·S + c + z)、探索の点数には (c + z) / a を足す |
| 学習 | 両方の席がこの補正で打つ探索 AI の自己対戦から、TD(λ) で学ぶ。目標は λ 収益（最後は勝敗）、損失は交差エントロピー |
| ファイル | `data/value-net.json`（6.4 MB）。`npm run rust-data` で `rust/engine/data/ai-data.json` に書き出し、svwb と WASM に埋め込む |
| コード | 推論 `rust/engine/src/ai/valuenet.rs`、学習 `scripts/td-main.ts`・`scripts/valueNet.ts`、自己対戦 `rust/engine/src/runner/td.rs`、カードの属性 `scripts/cardAttrs.ts` |

## 評価の式

```
S          = 手で作った評価（eval.rs の evaluate_with、重みは src/ai/data.ts の SEARCH_WEIGHTS）
z          = ネットワークの出力（局面の入力 x から）
勝つ確率   = σ(a·S + c + z)
探索の点数 = S + (c + z) / a
```

- S の単位は「点」。相手のリーダーの体力 1 が 1 点、自分のリーダーの体力 1 が 0.7 点、手札 1 枚が 0.6 点など（`DEFAULT_WEIGHTS`・`SEARCH_WEIGHTS`）。
  2026-10-27 から、学び直しは `td train --base zero` で S を 0 にして学ぶ（ユーザー判断。S ありと同じ強さだった。docs/ai-notes.md「評価関数の手作りの項を外す」）。
  今の既定のモデル（relearn8、2026-10-31 から）はこの形で、`baseWeights` は全部 0。探索の点数は補正 (c + z) / a だけになる（a は学習で動かない）。読みの中の相手の予想などの方策は、探索 AI の既定の重みのまま
- **a**（今 0.0126）: 評価 1 点あたりのロジット。79 点でロジット 1、勝率 50% のあたりでは評価 1 点が勝率 0.3 ポイントほど。
  学習で決める（`--fitA 1`。下限 0.005）。`td init` の既定は 0.08 で、学び直すごとに下がってきた（2026-10-14 の最初の採用のころは 0.04 ほど）
- **c**（今 0.460）: ロジットの切片。出力の層のバイアス b2（今 0.460）と同じ勾配で動くので、2 つは実質 1 つの切片（合わせて 0.921）
- 補正 (c + z) / a は S と同じ「点」の単位になり、探索は S と足した値で手を比べる
- 試合が終わった局面では補正は 0（S の勝ち負けの点だけ）

### 補正の大きさ（測った値）

共有フォルダの自己対戦 `data/selfplay/royal-9/f0.jsonl.gz`（2000 試合、14 デッキ。介入の試合とランダムに打った局面を除く）の局面を、その日の既定の補正 s2ba で採点した（2026-10-25。relearn7・relearn8 では測り直していない。relearn8 は S = 0 なので、S のばらつきの列は今の既定には当てはまらない）:

| 局面の種類 | 局面 | S のばらつき（標準偏差） | 補正の絶対値の平均 | 補正のばらつき（標準偏差） | ロジットでのばらつき a·S / c + z |
| --- | --- | --- | --- | --- | --- |
| ターン末 | 36,793 | 13.9 点 | 86.2 点 | 137.2 点 | 0.18 / 1.73 |
| 自分のターンの最初 | 35,086 | 17.2 点 | 86.4 点 | 131.8 点 | 0.22 / 1.66 |
| 想像の局面 | 68,959 | 19.6 点 | 77.4 点 | 111.2 点 | 0.25 / 1.40 |

- 局面どうしの違いのほとんどは補正が出している（ロジットでのばらつきは S の 7〜10 倍）。比較用の 7 デッキどうしの試合だけで数えても同じくらい
- ただし探索が手を選ぶのは、同じ局面から打てる並びどうしの点数の差。その差の中で S と補正がどう分かれるかは測っていない

## 形

```
入力 x（3506 個。ほとんど 0）
  ├ カード・クレストごとの入力  14 種類 × 248 = 3472
  └ 数値の入力                 34
        │  w1（3506 × 256）＋ b1
        ▼  ReLU
隠れ層 1（256）
        │  layers[0]（256 × 32）＋ b
        ▼  ReLU
隠れ層 2（32）
        │  w2（32）＋ b2
        ▼
z（1 つ）── (c + z) / a を S に足す
```

- 重みの数: w1 が 897,536（0 でないのは 586,082。3506 行のうち 0 でない行は 2290）、b1 が 256、2 つ目の層が 8,192 + 32、出力が 32 + 1、a と c
- 入力は疎なので、推論は 0 でない入力の行（256 個ずつ）だけを足す。1 局面の計算は 35 × 256 + 256 × 32 ≈ 1.7 万回の積和ほど
- 最初の層は、行がカード（とその種類）ごとに分かれている。だからカードごとの重みを属性で埋める（下の `td attr`）ことができる
- モデルの JSON の入力の並び（`zones`・`scalars`）は、今のコードの並び（`ZONES`・`SCALARS`）の部分列であればよい。入力を足す前の古いモデルもそのまま読める
- 作れるが今の既定には無い形:
  - 隠れ層 1 つ（2026-10-19 まで。大きさ 32）。`layers` が無いモデル
  - 場のカードのネットワーク（`board`）。場のカード 1 枚ずつを小さなネットワーク（32・16）に通して自分の場・相手の場ごとに足し、最初の層の入力の末尾に入れる。
    6 万試合で学んでも上乗せが無く、採っていない（「場のフォロワーごとのネットワーク」・「3 回目」・「4 回目」）

## 入力

評価する側のプレイヤー p から見た局面を入れる。名前の `my` は p、`opp` は相手。

入れないもの: 相手の手札（公開されたもの以外）と、山札の中身・順番。探索は決定化した局面（相手の手札と山札を並べ直したもの）を評価するので、
見えない情報を入れると、でたらめに並べた手札に点数が振り回される（テスト `input_ignores_hidden_information`）。

### カード・クレストごとの入力（14 種類 × 248 = 3472 個）

カード・クレストの一覧（`vocab`）は、`data/cards.json` の 241 枚（トークン 43 枚を含む）とクレスト 7 つ。
入力の添字は「種類の番号 × 248 + 一覧の番号」。同じカードが何枚もあれば値を足す（枚数になる）。

| 番号 | 名前 | 何を数えるか | 1 枚あたりの値 |
| --- | --- | --- | --- |
| 0 | `myHand` | 自分の手札 | 1 |
| 1 | `myHandBoost` | 自分の手札のスペルブーストの回数 | min(回数, 10) / 5 |
| 2 | `myBoard` | 自分の場のフォロワー・アミュレット | 1 |
| 3 | `myBoardCountdown` | 自分の場のアミュレットのカウントダウン | 残り / 3 |
| 4 | `myBoardEvolved` | 自分の場の、進化・超進化したフォロワー | 1 |
| 5 | `myCrest` | 自分のクレスト | 1 |
| 6 | `oppBoard` | 相手の場のフォロワー・アミュレット | 1 |
| 7 | `oppBoardEvolved` | 相手の場の、進化・超進化したフォロワー | 1 |
| 8 | `oppCrest` | 相手のクレスト | 1 |
| 9 | `oppHandRevealed` | 相手の手札のうち、公開されたもの | 1 |
| 10 | `myBoardAtk` | 自分の場のフォロワーの攻撃力（ターン中だけの増減も込み） | 攻撃力 / 5 |
| 11 | `myBoardDef` | 自分の場のフォロワーの体力 | 体力 / 5 |
| 12 | `oppBoardAtk` | 相手の場のフォロワーの攻撃力 | 攻撃力 / 5 |
| 13 | `oppBoardDef` | 相手の場のフォロワーの体力 | 体力 / 5 |

10〜13 は 2026-10-16 に足した。枚数だけでは、バフを受けたナイトと素のナイトを見分けられなかった（「補正の入力に攻撃力・体力を足す」）。

### 数値の入力（34 個、添字 3472〜3505）

おおよそ 0〜1 に収まるように割ってある。

| 名前 | 中身 | 割る数 |
| --- | --- | --- |
| `myHp`・`oppHp` | リーダーの体力 | 20 |
| `myMaxPp`・`oppMaxPp` | 最大PP | 10 |
| `myTurn`・`oppTurn` | そのプレイヤーのターン数 | 10 |
| `myPp` | 自分の今の PP | 10 |
| `myEp`・`mySep`・`oppEp`・`oppSep` | EP（エボルヴポイント）・SEP（スーパーエボルヴポイント） | EP 3・SEP 2 |
| `myExtraPp`・`oppExtraPp` | エクストラPP が使えるか | 0 か 1 |
| `myHandSize`・`oppHandSize` | 手札の枚数 | 9 |
| `myDeck`・`oppDeck` | 山札の枚数 | 40 |
| `myGraveyard`・`oppGraveyard` | 墓場の枚数（30 で頭打ち） | 20 |
| `after` | ターン末の局面でなければ 1（下の「局面の種類」） | 0 か 1 |
| `first` | 自分が先攻なら 1 | 0 か 1 |
| `myAtkSum`・`myDefSum`・`oppAtkSum`・`oppDefSum` | 場のフォロワーの攻撃力・体力の合計 | 20 |
| `myWard`・`oppWard`・`myBane`・`oppBane`・`myBarrier`・`oppBarrier`・`myAmbush`・`oppAmbush` | 守護・必殺・バリア・潜伏を持つフォロワーの数 | 2 |
| `imagined` | 想像の局面なら 1（同上） | 0 か 1 |

表の行は名前をまとめて書いたもの。入力の並びは `valuenet.rs` の `SCALARS` の順（`myHp`, `oppHp`, `myMaxPp`, … , `oppAmbush`, `imagined`）。

### 局面の種類

同じ局面でも、どの時点の局面かで入力の `after`・`imagined` が変わる（`ValuePhase`）。

| 種類 | `after` | `imagined` | どこで使うか |
| --- | --- | --- | --- |
| ターン末（`End`） | 0 | 0 | 探索のターン末の採点。ターン終了時の処理を進めた後の局面 |
| 自分のターンの最初（`After`） | 1 | 0 | 学習だけ（λ 収益を計算するときの「次の局面」）。探索は使わない |
| 想像の局面（`Imagined`） | 1 | 1 | 探索の読み直し。相手のターンを読んだ後の、自分の次のターンの最初 |

`imagined` は 2026-10-22 に足した。読みの中の相手は本物より甘く、読んだ後の局面を平均 6〜7 ポイント楽観していたので、そのずれを学ばせるため（「読みの中の相手のずれを学習で直す・資源の介入」）。

## 使われ方

### 探索 AI（`search`）

1. 自分のターン: ターン末までのビームサーチ（幅 512・深さ 16）の各終局面を、ターン終了時の処理を進めてから S + (c + z) / a（ターン末）で採点する
2. 読み直し: ターン末の点数の上位 4 つの最初の手について、相手の手札を 12 通り引き直し、相手のターンを幅 16・深さ 8 のビームサーチで打った後の局面を
   S + (c + z) / a（想像の局面）で採点して平均する。選ぶ点数は、これとターン末の点数を半分ずつ混ぜたもの（`rescoreMix` 0.5）
3. 読みの中の相手は補正を使わず、手で作った評価だけで打つ（`opponentSearch.extraEval` が false。足しても効かなかった。「棋譜の指摘: バックウッドかフェアリーか」）

探索の全体の形は [ai-notes.md](ai-notes.md)「今の AI」。

### ほかの所

- リノセウス用 AI（`rhino`）: 同じ補正に、リノセウスの打点の項（`RHINO_POTENTIAL`）を足して使う
- マリガン: 既定（`mulligan: "turn1"`・`mulliganTurns` 3、2026-10-26 から）は、返し方ごとに引き直した後、3 ターン目の自分のターンの終わりまで貪欲法で打ち進めた局面を
  S + 補正（ターン末）で比べる（`mulliganTurns` 0 なら 1 ターン目の最初の局面を S + 補正（ターンの最初）で）。`mulligan: "sample"` は引き直した直後の局面を S + 補正（ターン末）で比べる。
  手札の形のモデル（`mulligan: "model"`、2026-10-26 より前の既定）は補正を使わない
- 補正を使わない AI: `search-classic`、物差し（`yardstick`）、貪欲法
- 強い相手の物差しは、2026-10-22 の既定（s2b）の写し `rust/engine/yardstick/strong-1-net.json` を使う。既定を学び直しても動かない（[yardstick.md](yardstick.md)）
- 別の補正で打つ: `compare` 等の設定の JSON に `{"valueNet":"<ファイル>"}`、補正なしは `{"valueNet":false}`（[commands.md](commands.md)）
- 画面: リプレイ・サンドボックスの「AI の考え」で、点数の内訳（手で作った評価と補正）を見られる
- 埋め込み: `data/value-net.json` を `npm run rust-data` が `rust/engine/data/ai-data.json`（コミットしない）に書き出し、svwb と WASM に埋め込む。
  書き出した後に元のファイルが変わっていれば、ビルドは「埋め込むデータが古くなっています」で止まる（[rust/README.md](../rust/README.md)）。WASM は補正の分だけ大きい（8.3 MB）

## 学習

### 流れ

1. 自己対戦: 今の既定の補正を入れた探索 AI どうしで打つ（`svwb td selfplay`、6 万試合）
2. 学習: 今の補正から続けて学ぶ（`npm run td -- train`）
3. 後の処理: `td prune` → `td attr`
4. 判定: 今の既定と打ち比べる。採用なら `data/value-net.json` を置き換え、次の回はその補正で自己対戦を作る（学んだ評価で打って学び直す閉じた輪）

ここ数回の手順（[ai-notes.md](ai-notes.md)「今の AI」の「補正を学び直すときの手順」と同じ）:

```sh
# 自己対戦（ユーザーの PC で 3000 試合ずつ 20 回、28 並列で 4 時間ほど）
svwb td selfplay --model data/value-net.json --games 3000 --start <g> --eps 0.1 --opp beam --sampling default --iv 3 --ivZone both --imagined 2 --out d<i>.jsonl
# 学習（6 万試合で 45 分ほどの見込み。2026-10-30 に速くする前は 1 時間ほど）
npm run td -- train --model data/value-net.json --data d0.jsonl,...,d19.jsonl --out m.json --epochs 3 --lr 0.0003 --l2 0.001 --best 1 --bestOn end,imagined
# 後の処理
npm run td -- prune --model m.json --data d0.jsonl,...,d19.jsonl --out mp.json
npm run td -- attr --model mp.json --out mpa.json --keepA 0
```

### 自己対戦のデータ

- 両方の席が、学ぶ前の補正を入れた探索 AI（既定の読み方。`--sampling default --opp beam`）。比較用の 7 デッキの全 49 組を順に回す（`--decks` で変えられる）
- 各プレイヤーについて、自分のターンの最初（`"ph": 1`）、ターン末（`"ph": 0`）、想像の局面（`"ph": 2`。そのターンに選んだ並びの読み直しで作った局面から 2 つ、`--imagined 2`）を書く。
  各局面に S（`"s"`）、入力の添字と値（`"x"`・`"v"`）、場のカードの属性（`"b"`）がある
- 10% の確率で、自分のターンの最初の手をランダムに打つ（`--eps 0.1`）。その局面（`"ex"`）は学ばず、1 つ前の局面の目標もそこで切る
- 介入（`--iv 3 --ivZone both`）: 各試合で 1 つ、どちらかのプレイヤーの 3〜8 ターン目の自分のターンの最初から、手札か場のカードを 1 枚消した局面を 3 つ作り、
  そこから最後まで打った試合も書く。カードの価値を「その局面の後に勝ったか」の相関ではなく、消した結果から学ばせる（「介入データを TD 学習に混ぜる」・「場のカードを消す介入を混ぜる」）
- `"x"` は自己対戦に使ったモデルの入力の並びで書く。入力の並びを変えたモデルで学ぶなら、自己対戦を作り直すか `td extend` で並びを揃える。
  `"b"` は入力に直す前の値なので、場のカードのネットワークは作り直さずに学べる
- 量: 6 万試合で、ターン末と自分のターンの最初が 540 万局面ほど。想像の局面を入れると、学習に読む局面は 2 倍ほどになる

### 目標

プレイヤーごとに、局面は「ターンの最初 → ターン末 → 次のターンの最初 → …」と並ぶ（想像の局面は、直前のターン末に付く）。

```
G_t = (1 − λ) · V_{t+1} + λ · G_{t+1}     （λ = 0.7）
最後の局面の G = 勝敗（勝ち 1・負け 0）
V   = 今学んでいるモデルの予測 σ(a·S + c + z)。エポックの最初に全局面で計算し直す
```

- 次の局面がランダムに打った局面なら、G_t = V_{t+1}（そこで切る）
- 想像の局面の目標は、同じターンのターン末の局面と同じ（本物の次の自分のターンの最初からの λ 収益）。
  読みの中の局面と、その後に本物で起きたことを並べて学ぶことになる

### 損失と最適化

- 損失: 予測 σ(a·S + c + z) と目標 G の交差エントロピー。局面ごとの重みは、介入の試合が `--ivWeight`、想像の局面が `--imaginedWeight`（どちらも既定 1）
- 学ぶもの: 全部の重み・バイアスと、c・a
- Adam（β1 0.9・β2 0.999）、ミニバッチ 128 局面、学習率 0.0003（`--lr`）、3 エポック（`--epochs`）。
  重みの減衰 0.001（`--l2`。重みから直接引く形で、バイアス・c・a は減衰させない）
  読んだ局面に一度も出ない入力の行は更新しない（勾配が常に 0 で、`td prune` で 0 にする行。2026-10-30 から減衰もかけない。ai-notes.md「td train を速くする」）
- 確かめ用: 試合番号から決めた 1 割の試合を学ばずに取っておき、エポックごとに勝敗の交差エントロピー・AUC を出す。
  `--best 1 --bestOn end,imagined` で、ターン末と想像の局面（探索が点数に使う 2 つ）の交差エントロピーが一番小さいエポック（学習前も含む）の重みを書き出す
- 一から学ばず、今の補正から続けて学ぶ。同じデータなら続けて学んだ版のほうが少し強く、一から学ぶ 256・32 は 3000〜6000 試合ではデータが足りず弱かった
  （「大きなネットワークで一から学び直す」・「自己対戦を増やして補正を学び直す」）

### 学んだ後の処理

- `td prune`: 学習データに一度も現れなかった入力の行を 0 にする。学ばれずに初期値の乱数のまま残っているので、そのカードを使うデッキで補正がでたらめに動かないようにする
- `td attr --keepA 0`（リッジ回帰の罰 3）: カードの行を、カードの属性（`scripts/cardAttrs.ts`、今のカードで 156 個。種類・クラス・コスト・攻撃力・体力・キーワード・タイプ・
  能力のきっかけ × 効果のプリミティブ等。テキストは使わない）の線形和で当てはめ、学んでいない（0 の）行をその当てはめで埋める。
  初見のカードも、属性からそれらしい値で見られる（新しいデッキで +4.9 ポイント。「カードの重みを属性とカードごとの残りに分ける」）。
  最初の層は線形なので、埋めた行を w1 に書き込むだけで、推論は変わらない

### 判定

今の既定と `npm run compare`（同じシードで席とデッキを入れ替え、組の 2 試合を鏡にする）で 6000 試合ほど打ち、物差し 2 つ（`npm run yardstick`）とリノセウス用 AI も見る。
予測の精度（交差エントロピー・AUC）が良くなっても、勝率で確かめるまで採らない（予測が良くて勝率が下がった例が何度もある）。採ったらゴールデンテストを保存し直す。
決め方は [ai-notes.md](ai-notes.md)「判断のしかた」。

### モデルを作る・形を変える・中を見るコマンド

`npm run td -- <コマンド>`（引数は [commands.md](commands.md)「td」と `scripts/td-main.ts` の先頭）:

| コマンド | すること |
| --- | --- |
| `init` | 新しいモデルを作る。出力の重み w2 を 0 にするので、最初は補正 0。`--hidden 256,32` で隠れ層を重ねる（足す層は He の初期化） |
| `extend` | 入力を今の並びに広げる。足した行の重みは 0 なので、補正は変わらない |
| `widen` | 隠れ層 1 つのモデルを、補正を変えずに大きい形（例: 256・32）に移す |
| `board` | 場のカードのネットワークを足す（足した分の重みは 0） |
| `train`・`prune`・`attr` | 上の学習と後の処理 |
| `probe` | 入力を 1 つ増やしたとき（最大PP・EP を +1、手札にカードを 1 枚足す等）の補正の変化。補正が何を見ているかを調べる |
| `ivcheck` | 介入で測ったカードの価値と、補正の予測の差を比べる |
| `eval` | モデルどうしの予測を同じ局面で比べる |
| `check` | 自己対戦で書いた補正の値（Rust）と、学習側（TypeScript）の計算が同じか確かめる |

## 試して採らなかったこと

- 勝敗から直接学ぶ（ロジスティック回帰、学んだ評価で打ち直さない）: 基準の重みに勝ち越せない（「評価関数の学習」）
- 大きいモデル（256・32）を一から 3000〜6000 試合で学ぶ: データが足りず弱い。大きいモデルは 3 万〜6 万試合で初めて伸びた（「大きなネットワークで一から学び直す」・「今のモデルを広げて学習を続ける」）
- 場のフォロワーごとのネットワーク: 6 万試合でも上乗せなし（「場のフォロワーごとのネットワーク」・「3 回目」・「4 回目」）
- 同じ局面からの手の比べ合い（打ち比べの勝率）を学ぶ: 伸びない（「同じ局面からの手の比べ合いを学ぶ」）
- 資源（EP・SEP・リーダーの体力・最大PP）を ±1 した介入: 伸びない（「読みの中の相手のずれを学習で直す・資源の介入」）
- 12 万試合で学ぶ・学習率をさらに下げる: 伸びない（「4 回目」・「自己対戦を作らずに学び方を詰める」）
- カードの属性の重みを一緒に学ぶ（`train --attr 1`）: 知っているカードの行が速く動きすぎて悪くなる（「カードの重みを属性とカードごとの残りに分ける」）
- 読みの中の相手にも補正を足す: 効かない（「棋譜の指摘: バックウッドかフェアリーか」）

## 分かっている癖

- 手札の枚数を高く見る・最後の 1 枚を出すのを嫌う傾向がある（AFネメシスで手札を残す、手札がジェノだけの局面でジェノを出さない）
- 最大PP と EP の価値を、介入で測った値より低く見ている（最大PP は半分以下、EP は 6 割ほど）
- 自己対戦に無い局面は学べない。例えば、リーアムのために EP を残す局面が自己対戦にほとんど無いので、リーアムが手札にあっても EP を重く見ない（「補正はカードごとの EP の価値を学んでいるか」）
- 次のターンにリノセウスで倒しきる形で、とどめの道具（手札の森の神秘・招集、場の燐光の岩）を持つほど点を下げる
- 入力はカードの枚数が中心で、場にいる間に働く能力やエンハンスで育ったカードを見分けにくい

詳しくは [ai-notes.md](ai-notes.md)「分かったこと」の「学習した補正（TD 学習）」と「分かっている弱点・未着手の候補」。
