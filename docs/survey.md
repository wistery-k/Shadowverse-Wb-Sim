# 候補の打ち比べ調査（`npm run svwb -- survey`）

自己対戦の局面を無作為に取り、今の AI が作れる候補を、同じ乱数で最後まで打ち比べる調査。2026-11-11 から
（審査の文書「AI の設計の審査と今後の方針」課題点 3「先にやること: 候補の打ち比べ調査」、2026-11-10 の審査の「やる順番」の 2。その後の道筋は [STATE.md](STATE.md)「次」）。

- **何を測るか**: 伸びしろの 3 つの層（審査の文書の課題点 3）のうち、層 B「AI が作れる候補の中での選び直し」の大きさ。
  AI が手を選んだ後に、候補ごとに最後まで何十回も打って一番良いものを選び直したら、1 試合あたり何ポイント得か。あわせて、大きなミスの回数と、問題集に足す局面
- **判定役は最後まで打った勝ち負け**: 人間の記録にも、打った人の強さにも頼らない。続きは両方の席とも今の AI が打つので、
  「今の AI を 1 段だけ改善した打ち手」の得を測る（今の AI が両方の席で同じように読み違える局面は直らない。審査の文書の前提の但し書き）
- **シミュレータの中の試合だけ**: 局面は今の既定の AI どうしの自己対戦からだけ取る。実際の対戦の局面を入れる口は無い（CLAUDE.md「ソフト打ち」）

本体は `rust/engine/src/runner/survey.rs`。候補を作るのは `SearchAgent::survey_plans`（`rust/engine/src/ai/search.rs`）。

## 何をするか

1. **局面**: 今の既定の AI どうしの試合 g（デッキ・席・シードは `svwb ai-play`・`deep-gap` と同じ `ai_game_setup`）を打ち、
   両方の席の自分のターンの最初の局面から、試合番号と手の番号で決まる乱数で `--rate` の割合を選ぶ。**差の大きさでは選ばない**
   （差の大きい局面だけを選ぶと、たまたま悪いほうを引いた分が混ざる。deep-gap の 150 局面は点数の差 15.2 が最後まで打って 8.2 だった）
2. **候補**: 試合でその局面を考えたときと同じ乱数で今の AI に考えさせ（試合で打った手と同じ手を選ぶ。違えば行に `match: false`）、次を候補にする
   - **AI が読み直す候補**: ターン末の点数の上位 4 つの最初の手と、drawSplit が足す引く手（AI はこの中から選ぶ）。
     読み直しを始めたが rescoreRace が途中で打ち切った候補も、ここに入れる（`cut`。下の「本番の前に足した決まり（2）」）
   - **足す候補**: 同じ決定化のビームの終局面から、ターン末の点数の高い順に、使うカードの組（手札から出すカード・融合の素材の種類）が
     それまでの候補のどれとも違い、打つ手も違う並びを `--extra` 個（既定 4）。評価の読み違いで下に落ちている手を拾うため
     （同じ最初の手でも別の並びを拾う。deep-gap の試合 486 のジャンヌのように、最初の手ごとに 1 つしか読み直さないと落ちる並び）
3. **打ち方**: 候補ごとに `--m` 回（既定 32）最後まで打つ。r 回目は、手番の側から見た決定化（相手の手札・山札の中身と順番、乱数の状態）と
   AI の乱数がどの候補でも同じ。候補は、AI がその並びを選んだものとして打つ: 最初の手を打ち、次の判断からは局面が予想どおりなら並びの続きを打つ
   （並びは最初の引く手・ランダムな手までで、その先と並びを打ち終えた後は AI が考え直す。リーサルを見つければそれを打つ）。続きは両方の席とも今の既定の AI
4. **二段目（確かめ）**: 一段目の 32 回で、AI の選んだ候補との勝率の差が最も大きい候補の差が `--flag` ポイント（既定 10）以上なら、
   その候補と AI の選んだ候補だけを、一段目と重ならない乱数でさらに `--confirm` 回（既定 96）打つ

## 決まり（回す前に決めたこと。2026-11-11）

結果を見てから変えない。変えるなら、新しい決まりとして書き足し、前の決まりの結果も残す。

| 出すもの | 決まり |
| --- | --- |
| 打ち比べで選び直す得（1 局面） | 一段目の 32 回を偶数回と奇数回に分け、片方で勝ちの最も多い候補を選び（同じなら AI の選んだ候補）、もう片方で AI の選んだ候補との勝率の差を測る。両方の向きの平均。選ぶのに使った回で測らないので、選んだ偏りが入らない（16 回で選ぶ打ち手の得なので、もっと回数を掛けて選ぶ打ち手の得より小さい。下限） |
| 1 試合あたり | 1 局面あたりの得（打ち比べなかった局面は 0）× 1 試合 1 席の自分のターンの最初の局面の数（選ばなかった局面も数える）。片方の席が全部の自分のターンで選び直したときの見積もり（局面どうしの重なりは見ない） |
| 上位 4 つだけと 8 つ | 選べる候補を「AI が読み直す候補」だけにしたものと、足す候補を含めた全部 |
| 大きなミス | 二段目の回だけで、選び直した候補と AI の選んだ候補の差が 15 ポイント以上、かつ差の標準誤差（回ごとの差のばらつきから）の 3 倍以上。一段目の差は使わない |
| 問題集に足す局面の候補 | 大きなミスの局面（審査の文書の「打ち比べの差が 15 ポイント以上で、誤差の 3 倍を超えるもの」）。合格の条件は、局面と 2 つの並びを見て `npm run misses -- add` で手で書く（[misses.md](misses.md)） |
| 内訳 | デッキ（手番の側）、自分のターン（1〜3・4〜6・7〜9・10〜）、手の種類（一段目の 32 回で勝ちの最も多い候補と AI の選んだ候補の違い: 出すカード／進化・超進化／融合・能力・エクストラPP／攻撃先・手の順番だけ。読み直した候補か足した候補か）。2026-11-12 から、どの内訳にも二段目で測る得を出す（下の「本番の前に足した決まり（2）」の後の注） |

### 試しの後、本番の前に足した決まり（2026-11-11）

試し（下の「速さ」。10 試合・15 局面）で、上の「打ち比べで選び直す得」には 2 つの難点が見えた。どちらも結果の大きさではなく、測り方の性質。

- 16 回で 4〜9 つの候補から一番勝った候補に替えるので、AI の手が一番良い局面でも、偶然多く勝った候補に替えてしまう。替えた先は本当は少し悪いことが多く、得が負に出やすい
  （試しでは 1 局面 −1.67 ± 1.52）。負に出ても「層 B が無い」とは言えず、「16 回で選ぶ打ち手は AI より弱い」としか言えない
- ぶれが大きい（1 局面のばらつき 5.9 ポイント。1500 局面で 1 試合あたり ± 1.5 ほど。下の表の「小さい」を言うには足りない）

そこで、二段目を使う得を足し、下の「3 つの層」の表はこれで読む。前の決まりの得もそのまま出す（台帳の `gain4`・`gain8`）。

| 出すもの | 決まり |
| --- | --- |
| 二段目で測る得（1 局面） | 一段目の 32 回の全部で、AI の選んだ候補との差が最も大きい候補を選び、その差が `--flag`（10 ポイント）以上ならその候補に替える。測るのは二段目の 96 回（選ぶのに使っていない回）での差。二段目に回らない局面は 0。「32 回打って、10 ポイント以上勝ったときだけ替える打ち手」の得で、偏りはない（台帳の `gain2`） |
| うち足した候補の分 | 替えた候補が足した候補だった局面だけの分（`gain2Extra`）。残りは AI が読み直す候補に替えた分 |
| 1 試合あたり | 前と同じ（1 局面あたり × 1 試合 1 席の自分のターンの最初の局面の数） |

- 下の表の「上の端」は、平均＋標準誤差の 2 倍とする（前の決まりで書いていなかったので、ここで決める）

### 本番の前に足した決まり（2）: 読み直しを打ち切った候補（2026-11-11、審査のスレッドの指摘）

AI は上位 4 つを読み直すとき、引き直しを 3 通り読んで見込みの無い候補を打ち切る（`rescoreRace`）。初めの版は、打ち切った候補（選ぶときの値が無い）を
「AI が読み直す候補」に入れていなかった。試しの 14 局面を打ち切りなしで考え直すと、読み直しを始めた候補 56 のうち調査が入れたのは 38 で、
打ち切った 18 のうち 7 は使うカードの組が違うので足す候補として戻ったが、11（同じカードで順番だけ・進化と超進化だけが違う並び等）は打ち比べていなかった。
このままだと、層 B の下限がさらに下がり、「足した候補の分」に打ち切った上位 4 つの分が混ざる。

| 出すもの | 決まり |
| --- | --- |
| 候補 | 読み直す終局面（上位 4 つと drawSplit の引く手）のうち、選ぶときの値が無いものも「AI が読み直す候補」に入れ、`cut: true` の印を付ける。打つ手は足す候補と同じ作り方（drawSplit の区切りと deferFuse）。足す候補は、これらとも使うカードの組が違うものから選ぶ |
| うち打ち切った候補の分 | 二段目で測る得のうち、替えた候補が打ち切った候補だった局面だけの分（報告の表に出す）。`gain2Extra` は足した候補だけ |
| 半分の回で選ぶ得 | 「AI が読み直す候補だけ」（`gain4`）に打ち切った候補も入る |

- 2026-11-12、15 ポイント以上のミスの呼び方を「はっきりした見落とし」から「大きなミス」にした（ユーザーの提案。はっきりしているかは主観に寄るので、線で決まる名前に）。台帳の項目の名前（`misses` 等）はそのまま
- 本番の後（2026-11-12）、報告の内訳の表に二段目で測る得と二段目に回した局面の数の列を足した（初めの版の内訳は半分の回で選ぶ得だけで、
  読むのに使う得と違った）。決まりの表と読み方は変えていない。内訳の分け方（デッキ・ターン・一段目の回で決まる手の種類）は二段目の回を使わないので、
  どの内訳の二段目の得にも偏りはない
- 大きなミスの数え方は控えめ（下限）: 一段目で差が 10 未満に出た局面は二段目に回らない。本当の差が 15 の局面は、一段目の 32 回（差の標準誤差 10 ポイントほど）で
  10 以上に出るのが 7 割ほどで、二段目で 15 以上に出るのは半分ほど
- 打てなかった回（`x`。並べ直した局面で最初の手が打てない・途中で止まった）は、その回だけ両方の候補から除く（0 のはず）
- 引き分けは 0.5 勝

## 3 つの層と、どの結果ならどうするか

| 結果（1 試合あたり、二段目で測る得） | 読み方 | 次にすること |
| --- | --- | --- |
| 大きい（3 ポイント以上で、0 から標準誤差の 2 倍以上離れる） | 層 B が大きい。打ち比べで選ぶ打ち手は、今の AI よりはっきり強い | 打ち比べを先生役にする（検討モード、打ち比べの結果を学習に戻す）。足した候補の分が大きければ、読み直す候補に使うカードの組の違う並びを入れる案を compare で測る |
| 中くらい（1〜3 ポイント） | 層 B はあるが小さい | 大きなミスの局面を問題集に足し、手の種類の内訳から直す所を絞る。読み直しの改善は、内訳の多い所だけ束ねて測る |
| 小さい（1 ポイント未満、上の端も 1.5 未満） | 層 B はほぼ尽きた（読みを増やす層 A も尽きている）。残りは層 C（AI が候補にも作れない手） | 選び直しに手間をかけず、補正の入力の追加と広いデッキでの学び直し（STATE.md「次」の 3）に進む |

- 足した候補の分（`gain2Extra`。前の決まりでは上位 4 つだけの得と 8 つの得の差）が小さければ、AI の候補の作り方（ビーム）は足りていて、取りこぼしは選ぶ段（読み直し）にある
- 前の決まりの得（半分の回で選ぶ得）が二段目の得よりはっきり下なら、少ない回数で選ぶと偶然に引きずられる（打ち比べを先生役にするときは、回数と替える線を決めてから）
- 大きなミスが 1 試合 1 席 0.1 回以上なら、問題集に足して手の種類を見る。ほぼ 0 なら、AI は自分の候補の中ではっきりしたミスをまれにしかしない
- 人間が見つけたミス（見落とし問題集の問）が、この調査の候補と打ち方で拾える種類かは `npm run misses -- cover` で見る（[misses.md](misses.md)「cover」。
  2026-11-11 の 9 問では、今の AI が間違える 7 問のうち 6 問は合格の並びが候補に入り、512 回の打ち比べで 4 問が 15 ポイント以上、2 問が 7〜8 ポイント）

## コマンド

```sh
npm run svwb -- survey run --out 結果.jsonl --games a-b [--rate 0.1] [--m 32] [--extra 4] [--confirm 96] [--flag 10] [--batch 8] [--decks <デッキ>,…|@<デッキの組>] [--opts '<設定>']
npm run svwb -- survey report 結果.jsonl… [--label 名前] [--no-ledger] [--top 20] [--states <フォルダ>]
npm run svwb -- survey recheck 結果.jsonl… --out 打ち直し.jsonl [--m 32] [--peek 1] [--batch 16]
npm run svwb -- survey turns 結果.jsonl… --pos <試合>:<手の番号> [--stage 2] [--out 回ごと.jsonl] [--cards <カード名>,…] [--why <回>,… [--explain <回数>]]
npm run svwb -- survey values 結果.jsonl… --kifu <棋譜>[,<棋譜>…] --score '<設定>' [--reads 12] --out 候補.jsonl
```

| 引数 | 既定 | 意味 |
| --- | --- | --- |
| `--games a-b` | （要る） | 打つ自己対戦の試合番号の範囲 |
| `--rate` | 0.1 | 自分のターンの最初の局面を選ぶ割合（1 試合に両方の席で 19 局面ほどなので、0.1 で 1 試合 2 局面ほど） |
| `--m` | 32 | 一段目に候補ごとに打つ回数 |
| `--extra` | 4 | 足す候補の数 |
| `--confirm` | 96 | 二段目に打つ回数（AI の選んだ候補と、差の最も大きい候補の 2 つ） |
| `--flag` | 10 | 二段目に回す、一段目の差（ポイント） |
| `--batch` | 8 | まとめて打って書く試合の数の上限（大きさはそろえる。17 試合なら 6・6・5。止めたときに失うのは書いていない分だけ） |
| `--opts` | `{}`（今の既定） | 自己対戦を打つ AI、候補を作る AI、続きを打つ AI（両方の席）の設定。`compare` の A・B と同じ形。新しいプールでは新しいプールの補正と見込みを渡す（[yardstick.md](yardstick.md)「新しいプールの物差し」。今は補正 R5 の `pool-r5-net.json` と見込み R4 の `pool-r4-potential.json`、2026-11-21 までは `pool-r3-*.json`、2026-11-22 までは `pool-r4-*.json`）。試合の行に `opts` として書き、`report`（台帳の `a`）と `recheck` はそれを使う（違う設定の行が混ざっていれば断る）。2026-11-16 から |
| `--decks` | 比較用の 7 デッキ（`svwb ai-play` と同じ試合） | 並べたデッキ（`@<デッキの組>` も。[commands.md](commands.md)「compare」）で自己対戦を打つ。組とシードは `compare --decks` と同じ（先の席が A）。デフォルトデッキと違うデッキのマリガンは compare と同じ |
| `report --label` | なし | 台帳の名前 |
| `report --no-ledger` | なし | 台帳に書かない |
| `report --top` | 20 | 問題集に足す候補を出す数 |
| `report --states <フォルダ>` | なし | 問題集に足す候補の局面を `g<試合>-i<手>.json`（状態の JSON）で書く。`npm run misses -- add --state` に渡せる |
| `recheck --m` | 32 | 二段目に回した局面ごとに、AI の選んだ候補と替える候補を打ち直す回数（2026-11-12 に足した確かめ。下の「本番の結果」） |
| `recheck --peek` | 1 | 1 なら相手の手札を実際のまま（山札の中身と順番、乱数の状態は作り直す）、0 なら今までどおり引き直す。打ち比べの得が、引き直した世界だけのものでないかを見る |
| `turns --pos <試合>:<手の番号>` | （要る） | 打ち直す局面（結果の行の `g` と `i`）。下の「回ごとのターンの手順」 |
| `turns --stage` | 2 | 2 なら二段目（AI の選んだ候補と替える候補を `confirm.n` 回ずつ）、1 なら一段目（全部の候補を `m` 回ずつ） |
| `turns --out` | なし | 回ごとの行（JSON Lines。`plan` 候補の添字・`ai` AI の選んだ候補か・`r` 回・`result` 勝ち負け・`stored` 結果の行の勝ち負け・`turn` 始めのターンに打った手・`text` その説明） |
| `turns --cards` | なし | 並べたカードを、このターンにプレイした回としなかった回の勝率も出す |
| `turns --why` | なし | 並べた回（`r`）で、候補の並びを打ち終えた後に AI が初めて考え直す判断の局面と、AI が読む候補（読み直した候補・打ち切った候補・足した候補）の、選ぶときの値とターン末の点数を出す。同じ乱数で考え直させるので、選ぶ手は記録の手と同じになる（違えば書く） |

## 回ごとのターンの手順（`survey turns`。2026-11-19）

候補の並び（`steps`）は最初の引く手・ランダムな手までで、読んだ並び（`full`）もビームの終局面までなので、どちらもターンの終わりまでとは限らない。
打ち比べでは、並びの後を AI が考え直して打つ。なので、打ち比べで勝った「手順」は、結果の行だけでは分からない
（問題集の `witch-hold-g1066` で、良い手の後に AI が大遊戯世界とマナリアの魔弾を打っていたのに、条件を「打たない」にしていた。[misses.md](misses.md)「手順の候補の続きと 2 問」）。

`survey turns` は、結果の 1 局面の打ち比べ（既定は二段目）を、`run` と同じ乱数・同じ打ち方で打ち直し、回ごとに、始めのターンに実際に打った手
（候補の手と、その後に AI が打った続き。ターン終了まで）と勝ち負けを数える。測るもの・乱数は変えないので、勝ち負けは結果の行と同じになる
（調査を打ったときからエンジン・AI が変わっていなければ。一致した回の数を出す）。打ち方の記録（`PlayoutLog`）に始めのターンの手を足しただけで、`run` の出力は変わらない。

```sh
npm run svwb -- survey turns survey-2.jsonl --pos 1066:102 --out 回ごと.jsonl --cards マナリアの魔弾,大遊戯世界
```

出力は、候補ごとの「このターンの手順」の表（回数・勝ち・勝率。選ぶ手は直前の手にまとめる）と、出したカードの並びの表（攻撃・選ぶ手を除く）、
`--cards` ならカードをこのターンにプレイした回としなかった回の勝率。
