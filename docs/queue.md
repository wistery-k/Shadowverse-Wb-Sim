# ジョブのキュー（`npm run queue`）

ユーザーの PC で対戦を回す道具。ジョブを並べたファイル（券）を積み、積んだ順に、ジョブを 5〜10 分の区切りに分けて回し、区切りごとに結果を残す。
回す係は pueue（https://github.com/Nukesor/pueue。下の「キュー（pueue）」）。

- **積む**のは、スレッドが `plan` で出した 1 行（`queue.sh add svwb-queue-1 …`）を、ユーザーがホストで流すだけ。積むだけでは回らない（CPU を使わない）。
  いくつ積んでもよく、積んだ順に回る。同じ券を 2 回流しても増えない。スレッドは積むコマンドを示すだけで、積むかはユーザーが決める
- **回す・止める**のは、積むのとは別。ユーザーが回したいときに `queue.sh start`（全部済むか止めるまで回る。`--until 07:00` でその時刻に一時停止）、
  止めたいときに `queue.sh pause`（回していた区切りは凍らせ、次の `start` で続きから）。いつ回すかはユーザーが決める（昼はゲームがカクつくので、ふつうは夜。2026-11-10）。
  PC やコンテナの起動で勝手には始まらない
- 電源が切れても、失うのは回していた区切りだけ。次の `start` がその区切りから回し直す
- 結果: 回の task が終わると（失敗した区切りがあっても）、最後の task が台帳の行をブランチ `night/<回の名前>` にコミットし、棋譜などを出口のフォルダ
  （`~/svwb-data/outbox/<回の名前>/`）にまとめる。途中で止まっている回は `queue-push.sh` が済んだ分をまとめる。ユーザーはホストで push を 1 つ流すだけ（下の「止まったときのまとめ」）
- 前のやり方（1 晩分の券 `svwb-night-1` と `go`・`start <ファイル>`・`resume`・`stop`・`finish`。止める時刻を券に持っていた）は、
  PC でキューを何度か回してうまくいったので、2026-11-25 に外した（ユーザーの依頼）。前のやり方で回した回のフォルダは `status`・`list`・`wrap <名前>` で読め、
  `@run:<回の名前>` でそのファイルも読めるが、続きは積めない
- 本体は `scripts/night-main.ts`（pueue とのやり取りは `scripts/night-pueue.ts`、出口のまとめと展開は `scripts/night-outbox.ts`）。
  テストは `tests/night.test.ts`（svwb と pueue の代わりに偽物を回して、券・区切り・積み直し・まとめを確かめる。pueue の無いところでも回る）と
  `tests/night-queue.test.ts`（pueue が入っていれば本物の pueue で、積む・回す・一時停止・落ちる・失敗するを確かめる。無ければその部分は飛ばす）
- 自己対戦から学習・判定までの学び直しの流れも 1 つの券に並べられる（下の「学び直しの流れ」）
- 名前: 2026-11-24 に「夜のキュー」から「キュー」に改めた（夜に回すかはユーザーが決めるので。ユーザーの依頼）。コマンドは `npm run queue`・`queue.sh`・`queue-push.sh`
  （前の名前の `npm run night`・`night.sh`・`night-push.sh` は 2026-11-25 に消した）。
  ファイルの名前（`scripts/night-*.ts`・ジョブのファイルの置き場所 `night/`）・回の置き場所 `~/svwb-data/night/`・結果のブランチ `night/<回の名前>`・
  環境変数 `SVWB_NIGHT_*` は、前の回と上げたブランチと続けて使えるように、そのままにした

## ユーザーの手順（1 ページ）

どれもホスト（WSL の Ubuntu）の端末で流す（どのフォルダからでもよい）。コンテナ（`docker compose up -d`）が動いていること。
下の `queue.sh` は `~/Shadowverse-Wb-Sim/docker/remote-control/queue.sh` のこと。

0. **初めの 1 回だけ**: コンテナに pueue を入れる（数分）。回している回が無いときに

   ```sh
   cd ~/Shadowverse-Wb-Sim && git pull && cd docker/remote-control && docker compose up -d --build
   ```

1. **積む（いつでも）**: スレッドが計画の表と、`~/Shadowverse-Wb-Sim/docker/remote-control/queue.sh add svwb-queue-1 …` で始まる 1 行を示す。
   積むなら、その 1 行をそのまま貼って流す。積むだけで回らない。いくつ積んでもよい（積んだ順に回る）

   ```sh
   ~/Shadowverse-Wb-Sim/docker/remote-control/queue.sh add svwb-queue-1 name=… branch=… commit=… jobs=… plan=…
   ```

2. **回す**: 回したいときに次を流す。積んであるものを先頭から順に、全部済むか止めるまで回す（端末は閉じてよい）。
   決めた時刻に止めたいなら `--until 07:00`（その時刻に一時停止する）

   ```sh
   ~/Shadowverse-Wb-Sim/docker/remote-control/queue.sh start
   ```

3. **止める**: `queue.sh pause`。すぐ止まる。回していた区切りは凍らせてあり（CPU は使わない。メモリは持ったまま）、次の `queue.sh start` で続きから回る。
   `queue.sh pause --wait` なら、回している区切りが済んでから止まる（凍らせない）
4. **結果を上げる**: 回が済んだ後か、止めた後に、ホストで次を流し、スレッドに「push した」と伝える。全部済んだ回も、途中で止まっている回も、済んだ区切りの分が上がる

   ```sh
   ~/Shadowverse-Wb-Sim/docker/remote-control/queue-push.sh
   ```

   様子だけ見たいときは `queue.sh status`（キュー全体）・`queue.sh status <回の名前>`。積んだ回をやめるなら `queue.sh remove <回の名前>`
5. **棋譜・モデルなどが要るとき**（スレッドに言われたときだけ）: エクスプローラーで `\\wsl.localhost\Ubuntu\home\<ユーザー名>\svwb-data\outbox\<回の名前>`
   を開き、中のファイルを全部スレッドに上げる（中の `案内.txt` に、ファイルの数と大きさと結果の表がある）。取り込みが済んだら、そのフォルダは消してよい

## 流れ（スレッドから見て）

1. **積むコマンドを示す**: 変更を作業ブランチに push し、ジョブのファイルを書く（下の「ジョブのファイル」。ブランチの `night/` に置いてコミットし、push する）。
   `npm run queue -- plan <ファイル> --machine svwb-docker` で PC での見込みと積むコマンドを出し、表と `~/Shadowverse-Wb-Sim/docker/remote-control/queue.sh add …` の 1 行を
   そのまま示す。積んでよいかは聞かない（積むかはユーザーが決める。CLAUDE.md「実験を回す場所」。ユーザー決定 2026-11-24）。
   スレッドは `add`・`start` を流さない。積むコマンドが出ないとき（「積むコマンドは出していません: …」）は、書いてある理由（コミットしていない・push していない）を直して流し直す。
   表の終わる時刻は今から始めたときのもの（`--at 23:00` で始める時刻を替えられる）。キューに前から積んであるものの残りは、ユーザーに `queue.sh status` を見てもらうか、
   前の券の見込みから足す
2. **回す・止める**: ユーザーが `queue.sh start`・`queue.sh pause` を流す。止めた回の続きは次の `start` で回る
3. **結果**: 回の task が終わると（失敗した区切りがあっても）、その回の最後の task（まとめ）が台帳の行をブランチ `night/<回の名前>` にコミットし、棋譜などを出口のフォルダにまとめる。
   途中で止まっている回（一時停止・止める時刻・電源が切れた）は、`queue-push.sh` が済んだ区切りの分をまとめる（下の「止まったときのまとめ」）。
   ユーザーがホストで `docker/remote-control/queue-push.sh` を流し、スレッドが `npm run queue -- ingest <回の名前>` で作業ブランチの台帳に足してコミットする。
   続きを回した後も同じ（残りの区切りの行が次のコミットになる）。棋譜・モデルなどが要るときだけ、出口のフォルダのファイルを上げてもらい、
   `npm run queue -- ingest <ファイル…>` で共有フォルダに展開する
4. **失敗した回**: 区切りが失敗すると、そのジョブの残りの区切り（と、そのジョブの作るファイルを読む後ろのジョブ）は回らず、ほかのジョブと後ろの券は回る。
   `queue.sh status` に「積んでいない N 区切り」と出る。直したら、`queue.sh add <回の名前>` の 1 行を示す（済んでいない区切りを積み直す。キューの後ろに付く）

1 つの回は 1 つのコミットで回す。違う版どうしは、新しい読み方を設定の項目にして既定を切っておけば、同じコミットの compare で比べられる（今までと同じ）。
違うコミットの回は、券を分けて積む（回ごとに、そのコミットのソースを回のフォルダの `src/` に出して、そこで svwb を組み立てる）。

## コマンド

```sh
npm run queue -- plan <ジョブのファイル> [--threads N] [--machine 名前] [--chunk-min 7.5] [--tz Asia/Tokyo] [--at 23:00] [--until 07:00] [--name 名前]   # 見込みと積むコマンド
# キュー（コンテナの中で。ホストからは docker/remote-control/queue.sh <同じ引数>）
npm run queue -- add <券|回の名前>                                     # 積む（いつでも。回の名前なら済んでいない区切りを積み直す）
npm run queue -- start [--until 07:00|+2h] [--tz Asia/Tokyo]          # キューを回す（全部済むか pause まで。--until でその時刻に一時停止）
npm run queue -- pause [--wait]                                        # キューを一時停止（回している区切りは凍らせる。--wait なら済んでから）
npm run queue -- status [名前]                                         # 名前なしはキュー全体
npm run queue -- remove <回の名前>                                     # まだ回していない task をキューから外す
npm run queue -- wrap [名前|--pending]                                 # 止まったときのまとめをやり直す（電源が切れた回・まとめが失敗したとき。--pending はまとめていない回を全部）
npm run queue -- ingest <回の名前|ファイル…> [--ledger 台帳] [--to /mnt/project-files] [--remote origin]   # スレッドで
npm run queue -- list
```

| 引数 | 既定 | 意味 |
| --- | --- | --- |
| `add <券>` | | 券の回を作り、組み立て・区切りごと・まとめの task を積む（下の「キュー（pueue）」）。同じ券をもう一度流しても増えない |
| `add <回の名前>` | | その回の済んでいない区切りのうち、キューに無いもの（失敗した・取り消した・`remove` した）を後ろに積み直す |
| `start --until` | なし（止めない） | キューを回し、その時刻にキューを一時停止する（回していた区切りは凍らせる）。付けなければ全部済むか `pause` まで回る。`start` を流し直すと前の止める時刻はやめる。昼かは聞かない（いつ回すかはユーザーが決める） |
| `pause --wait` | なし | 付けなければ、すぐ一時停止する（回している区切りを凍らせる）。付けると、回している区切りが済んでから止まる |
| `plan --at`・`--until` | 今から・なし | `plan` の表の見込みだけに使う、始める時刻と止める時刻（券には入らない）。書き方は `start --until` と同じで、`HH:MM` は時刻帯（`--tz`、既定 `Asia/Tokyo`。コンテナの時計は UTC）で次に来るその時刻。`+90m`・`+2h`（今から）や ISO の日時も書ける |
| `--threads N` | そのマシンの全部 | 使うスレッド数（svwb の `THREADS`）。結果は変わらず、速さだけが変わる。`plan` に渡すと券に入る |
| `--machine 名前` | このマシン | `plan` の見込みに使うマシン（PC は `svwb-docker`）。そのマシンの決めておいたスレッド数も使う |
| `--chunk-min` | 7.5 | 区切りのおよその長さ（分）。見込みから区切りの大きさを決める。`plan` に渡すと券に入る（`chunk`） |
| `plan --name` | `<ジョブのファイルの名前>-<日付>` | 券の回の名前（回のフォルダの名前）。英数字と `.` `_` `-` だけ |
| `ingest <回の名前>` | | スレッドで。GitHub からブランチ `night/<回の名前>`（`night/<回の名前>` と書いてもよい）を取ってきて、その回の行のうち台帳にまだ無いものを足す（`--ledger` の台帳、既定は `docs/ledger.jsonl`）。コミットはスレッドが |
| `ingest <ファイル…>` | | スレッドで。上がった出口のファイル（名前が変わっていてよい。案内は読み飛ばす）を確かめて、`--to`（既定 `/mnt/project-files`）の `data/…/<回の名前>/`・`logs/<回の名前>/` に展開する |

回は `~/svwb-data/night/<名前>/` に置く（環境変数 `SVWB_NIGHT_DIR` か `--root` で替えられる）。`wrap` は名前を省くと最後に作った回をまとめる。

## ジョブのファイル

1 行 1 ジョブで、svwb のコマンドと同じ形（`compare`・`yardstick`・`profile`・`misses`・`survey`。行の頭の `svwb` は書いても書かなくてもよい）。
学び直しの流れ（自己対戦・学習・後処理）のジョブ（`td selfplay`・`beam-gap`・`td`・`potential`・`pick`）は下の「学び直しの流れ」。
`#` から行の終わりまでは書き添え。上から順に回す。例:

```sh
# 定例（night/routine.txt を先頭に写してもよい）
yardstick --ref strong --opts '{}' --games 4000 --start 0 --label 定例-強い相手
# 補正の入れ替え（1.1 万試合で 1 ポイントを見る）
compare 5600 '{"valueNet":"data/models/x.json"}' '{}' 200000 --label 補正x
profile --games 49
```

- **compare**: `compare <試合数> '<A>' '<B>' [最初の試合番号] [B のデッキ] [--no-mirror] [--decks …] [--with <デッキ名> | --without <デッキ名>] --label 名前`（`npm run compare` と同じ。
  `--with` はそのデッキの絡む組だけ、`--without` は絡まない組だけ。試合番号はその組の k 番目の番号）
- **yardstick**: `yardstick [--ref classic|strong|pool-v0|pool-r3] [--opts '<設定>'] [--games 1000] [--start 0] --label 名前`
- **profile**（速さ）: `profile [--opts '<設定>'] [--games 49] [--start 0] [--rhino] [--decks <デッキ>,…|@<デッキの組>]`。結果は回のフォルダの `speed-<番号>.md`・`.json`（`svwb profile` の報告。`--decks` なら型ごとの表も出る。PP を残して終えたターンの割合などを、学び直しの回ごとに見るのに使う）
- **misses**（見落とし問題集、`docs/misses.md`）: `misses [run] [--opts '<設定>'] [--trials 24] [--seed 1] --label 名前`。分けずに 1 区切りで回す。
  見込みの「1 試合」は、全部の問を 1 回ずつ解く秒（台帳の前の回から、問の数の違いを割り直して見込む）。`--only`・`--dir`・`--out` は使えない（問題集全体を解く）
- **survey**（候補の打ち比べ調査、`docs/survey.md`）: `survey [run] --games a-b [--rate 0.1] [--m 32] [--extra 4] [--confirm 96] [--flag 10] [--batch 8] [--opts '<設定>'] [--decks …] --label 名前`
  （`--games N --start S` でもよい。`--opts`・`--decks` は新しいプールの AI とデッキで打つ用。2026-11-16 から）。試合番号の範囲で区切り、どの区切りも回のフォルダの `survey-<番号>.jsonl` に足す（1 つの番号で 1 試合。
  見込みの「1 試合」は、その試合から取った局面の打ち比べを含む秒）。区切りごとの台帳の行は無く、ジョブの区切りが全部済んだ後のまとめ（回の最後の task）が
  `svwb survey report` で 1 行を足す（報告は `survey-<番号>.md`、問題集に足す候補の局面は `survey-<番号>-states/`）。`--out` は使えない
- `--label` は compare・yardstick・misses・survey に要る（区切りの結果を後で足し合わせ、台帳を引くため）。比べの案ごとに付ける
- 試合番号（シード）の範囲は、前の回と重ならないように選ぶ（同じ試合を 2 回数えない。`npm run ledger -- runs --grep <名前>` で前の範囲を見る）
- キューでは使えない引数: `--no-ledger`（結果は台帳から集める）・`--kifu`・`--replays`・`--no-kifu`（棋譜はキューが回のフォルダの `kifu/` に書く。下の「回のフォルダ」）・`yardstick --record`
  （物差しの表に足すのは、終わった後に足し合わせた数字で）・`profile --json/--report/--baseline/--record`（キューが回のフォルダに書く）
- `--est <秒>`: 1 試合の見込みの秒（回すマシン・スレッド数で）。キューだけが読む。読み方を大きく変える設定（深い読み等）で、台帳にまだ回が無いときに。
  `td`・`potential` は全体の秒

### 学び直しの流れ（2026-11-13）

自己対戦から学習・後処理・判定の compare までを 1 つのキューに並べる（例は `night/relearn-b.txt`、小さく試すのは `night/relearn-b-small.txt`）。
ファイルは回のフォルダに作り、ジョブの行では `@/` と書く（`@/s-3.jsonl.gz` 等。設定の JSON の中にも書ける）。`{1..20}` は `1,2,…,20` のカンマ区切りに開く
（`--data @/s-{1..20}.jsonl.gz`）。

- **td selfplay**: `td selfplay --games N [--start S] --chunk C --out @/s-{k}.jsonl.gz --est <1 試合の秒> [ほかの引数]`。C 試合ずつ（大きさはそろえる）の区切りで、
  `{k}` に区切りの番号（1 から）を入れたファイルに書く。`.gz` なら書き終えた後にキューが gzip する。区切りの大きさは時間でなく `--chunk` で決める（後のジョブがファイルの名前で読むので）
- **beam-gap**（見込みの学びのデータ）: `beam-gap --games N --from S --chunk C --inputs @/pot-{k}.jsonl [--out @/pot-{k}-rows.jsonl] --est … [ほかの引数]`。区切り方は td selfplay と同じ
- **td**・**potential**（TypeScript の学習。`npm run td`・`npm run potential` と同じ引数）: `td train … --out @/n.json --est <全体の秒>`。1 つのジョブが 1 区切りで、
  `--out` のファイルを作る。途中からは続けられない（`pause` なら凍らせて続くが、電源が切れる・中断すると次は最初から）。
  組み立てのときにスクリプトをビルドして回のフォルダの `bin/td/`・`bin/potential/` に置き、それを回す（回している間にチェックアウトが替わっても同じコード）
  `td train`・`td prune` の行は、Rust 版（`svwb td train`・`prune`。同じモデルを書き、速くてメモリが少ない。[commands.md](commands.md)「svwb」）を
  回のフォルダに写した svwb で回す（2026-11-15 から既定。B の 6 万試合で TypeScript 版と同じモデルになるのを確かめた）。実験用の引数（`--attr` 等）を使う行は
  `--impl ts` を付けて TypeScript 版で回す（Rust 版はその引数をエラーにする）。2026-11-14 までの行（`night/relearn-b.txt` 等）は、`--impl` が無ければ TypeScript 版で回したもの。
  `--est` は TypeScript 版の時間のままの行が多い（多めに見積もる分には困らない）。PC の Rust 版の実測は、段階 4 の R1（新しいプールの自己対戦 6 万試合、入力あり）で
  学習 14 分・間引き 24 秒（`night/pool-r2.txt` の `--est` はこれから）
- **pick**: `pick --compare <前の compare の台帳の名前> --pass <ファイル> --fail <ファイル> --out <ファイル>`。その compare の済んだ区切りをまとめ、
  A の勝率 − 50% − 2 SE が 0 より大きければ `--pass`、そうでなければ `--fail` のファイルを `--out` に写す（回す前に決めた線で、後のジョブの設定を選ぶ）。
  結果は回のフォルダの `pick-<番号>.json` と、`status`・まとめの表
- 作るファイル（td selfplay・td branch・beam-gap は区切りのファイル、td・potential・pick は `--out`）は、途中は `.tmp` に書き、済んでから名前を替える。
  ファイルがあれば、印が無くても済んだものとする（手でファイルを置けば、そのジョブを飛ばせる）
- `@/` のファイルは前のジョブが作るものだけを読める（ジョブのファイルを読むときに確かめる）。回すときに前のジョブが作るはずのファイルが無ければ
  （失敗した・まだ済んでいない）、そのジョブを回さずに失敗にする。`add <回の名前>` で積み直すと、失敗したジョブから続きを回す。
  そのジョブの最初の区切りは、前のジョブの区切りが済むのを待つ（前のジョブが失敗すれば回らない）
- 組み立ての確かめでは、`@/` のモデルを今の既定（`valueNet` は `data/value-net.json`、`potentialNet` は `data/potential-net.json`）にして設定を読み、
  td selfplay・td branch・beam-gap は 0 試合で回す（td branch は 0 試合なら棋譜を読まない）。td・potential・pick の引数は確かめない（小さく試してから PC に回す）
- **前の回のファイル**（2026-11-22）: `@run:<回の名前>/<ファイル>` は、同じ根（`~/svwb-data/night/`）の下の、前の回のフォルダのファイル
  （`td extend --model @run:r6-heads-1/w.json --out @/h.json`。前の回で作ったモデルを次の回で読む）。PC の中の道を公開のジョブのファイルに書かないための書き方で、
  `@<ファイル>`（デッキの組のファイル）とは別。回の名前は英数字と `.` `_` `-`、ファイルは回のフォルダの中だけ（`..` は書けない）。
  前のジョブが作らなくてよいが、組み立てのときに無ければ組み立てが失敗する（その回の区切りは回らない）。前の回の task がキューに残っていれば、組み立てがそれを待つ。確かめの間のモデルの扱いは `@/` と同じ。
  学びのデータも書ける（`--data @run:r6-heads-1/s-{1..20}.jsonl.gz,@run:lethal-heads-1/s-{1..20}.jsonl.gz`。`{a..b}` を開いた 1 つずつを始める前に確かめる）

## 見積もりと区切り

1 試合の秒を、次の順に見積もる。

1. `--est`
2. 台帳（`docs/ledger.jsonl`）の、同じ比べ（種類・両方の設定・絞り込み・鏡・相手）・同じマシンの最近の 5 回。同じスレッド数の回があればその速さ、

区切りの大きさは、見込みで `--chunk-min` 分ほどになる組の数（大きさはそろえる）。区切りは最初の `add` のときに決めて `plan.json` に書き、

## 止まり方と再開

区切りの印と、印が無いときの作り直し。キュー全体の止まり方（一時停止・電源が切れた・失敗の後）は下の「キュー（pueue）」の「止まり方」。

| こと | どうなるか |
| --- | --- |
| 区切りが済んだ | 台帳の行（回のフォルダの `ledger.jsonl`）を書いた後、`done/<区切り>.json` の印を書く（どちらも fsync）。印のある区切りの task は何もしない |
| 台帳の行を書いた直後に電源が切れた（印が無い） | 次にその区切りの task が回ると、台帳に同じ引数の行があれば回さずに印を作る（survey は、出力に区切りの試合が全部あれば） |
| survey の区切りが途中で止まった | 書いた試合（`--batch` 試合ごとに書く）は残る。回し直すと、出力に既にある試合を飛ばして続きから |
| 区切りが失敗した（svwb が 0 以外で終わった） | `failed.json` と `status` の「メモ」に出る。直したら `add <回の名前>` で積み直す |
| 作るファイルができた直後に電源が切れた（印が無い） | 作るファイルがあれば回さずに印を作る（学び直しの流れのジョブ） |
| 前のジョブが作るファイルが無い | そのジョブを回さずに失敗にする（「入力がありません」）。前のジョブを積み直せば（`add <回の名前>`）、続けて回る |

- 回すのは組み立てのときに回のフォルダに写した svwb（`bin/svwb`）。回している間にほかのセッションが同じ `/workspace` で組み立て直しても、
  続きが後の日でも、同じコードで回る。台帳の行のコミットとブランチは券のもの（`SVWB_COMMIT`・`SVWB_BRANCH`）
- 設定の中のファイル（`"valueNet":"…json"` 等）は、回すたびにリポジトリから読む。回している間はそのファイルを替えない（台帳の `files` に中身の指紋が残る）
- コンテナ（`docker/remote-control`）が止まると、中のキューも止まる。`compose.yaml` は、`claude remote-control` が終わっても（ネットワークが切れた等）
  コンテナを止めずに中で立ち上げ直す形にしてある（2026-11-10。前の形では、`claude` が終わるとコンテナごと立ち上げ直り、キューが止まった）。
  この形にするには、一度ホストで `docker compose up -d` を流してコンテナを作り直す。PC の再起動・`docker compose down`・作り直しでは止まる（次の `start` で続きから）
- 2026-11-12 の朝（打ち比べ調査の本番、58 区切りの 57 番目の途中、05:19）に、PC の電源は入ったまま Docker が止まっていた。
  コンテナから見えるカーネル（WSL2 の VM）は朝に起動し直されていて、コンテナだけでなく VM ごと止まっていた。Windows Update の更新が原因らしい（ユーザーの見立て）。
  失ったのは回していた区切りの書いていない 7 試合だけで、朝に `resume` で残り 9 試合を回した。
  ユーザーが同じ日に Windows Update の「アクティブ時間」を夜を含むように設定した（その間は更新による自動の再起動をしない。再起動の要らない更新まで止まるかは分からない。
  長い回の夜に止まるのが続くなら、その夜だけ「更新の一時停止」も足す）。止まった朝は `/proc/uptime` で、VM ごと止まったのかキューだけが落ちたのかを見分ける
- 止める時刻を替える: `queue.sh start --until <時刻>` を流し直す（前の止める時刻はやめる）。止める時刻をやめるなら `--until` を付けずに `start`

## キュー（pueue）（決めたこと、2026-11-23。2026-11-24 に直し、2026-11-25 に前のやり方を外した）

ユーザーの希望（2026-11-23）: 券 1 つの長さを夜の長さに合わせなくてよいように、「ジョブを積むのはいつでもいくらでも、停止・再開はそれとは関係なく」。
回す係に pueue を使う形をユーザーが選んだ。券・計画の指紋・区切り・台帳の行・止まったときのまとめ・朝の push は今までのものを使い、
pueue には「積んだ順に 1 つずつ流す・止める・続ける・落ちた後に何を回していたかを覚えておく」だけを任せる。

**券**は `svwb-queue-1 name=<回の名前> branch=<ブランチ> commit=<sha の頭 12 桁> jobs=<ジョブのファイル> plan=<計画の指紋>`
（`threads`・`chunk` は `plan` に渡したときだけ入る）。止める時刻（`until`・`tz`）を持たない（書いてあれば断る）。
計画の指紋は、ほかの項目とジョブのファイルの中身の sha256 の頭 12 桁（前のやり方の券 `svwb-night-1` と同じ作り方。`add` はその券を断る）。
`plan` は、ジョブのファイルをコミットしてあり、コミットしていない変更が無く、今のコミットを `origin/<ブランチ>` に push してあるときだけ券を出す。
ユーザーがホストで流すのは `docker/remote-control/queue.sh`（中身は `docker compose exec -T rc npm run -s queue -- <引数>`。ユーザーの決定 2026-11-19:
Windows のショートカットではなく、`docker compose exec` で流す .sh にする）。
スレッドは積むコマンド（`queue.sh add <券>` の 1 行）を示すだけで、積んでよいかは聞かない。積むのも回すのもユーザー（CLAUDE.md「実験を回す場所」。ユーザー決定 2026-11-24）。

**pueue の置き方**（`docker/remote-control`）:

- `Dockerfile` が `cargo install --locked pueue@4.0.5` で入れる。版は固定する（4.0 で状態の形が変わり、前の版の状態は読めない。上げるときはキューが空のときに）
- `compose.yaml` の `command` が、デーモン（`pueued`）を立てる（落ちたら 10 秒後に立て直す）。`claude remote-control` の繰り返しとは別
- 設定は `PUEUE_CONFIG_PATH=~/svwb-data/pueue/pueue.yml`（無ければ `entrypoint.sh` が作る）。状態とログは `~/svwb-data/pueue/`（コンテナを作り直しても残る）、
  つなぐ口（socket）と pid は `/tmp/pueue-<UID>/`（起動のたびに前のものを消す。コンテナの pid は使い回されるので、前の pid が残っていると立ち上がらない）
- 組（group）は 2 つ。`svwb`（同時に 1 つ。区切りを回す）と `svwb-ctl`（同時にいくつでも。止める時刻の task）。最初の `add` が作り、作った `svwb` は一時停止にしておく。
  pueue はデーモンが立ち上がり直すと、これから回る task のある組を止めたままにするので、PC やコンテナの起動で勝手に始まらない

**`add <券>` がすること**（コンテナの中で。`/workspace` のチェックアウトの `night-main.ts` が流れる）:

1. 券を読む。知らない形（`svwb-queue-2` など）なら、ホストで `git pull` してから流すように言う
2. 券のコミットが `/workspace` の git に無ければ、GitHub から券のブランチを取ってくる（リポジトリは公開なので https で。コンテナに認証情報は要らない。
   `origin` が `git@github.com:…` でも https の形に直して取る）。取ってきても無ければ断る
3. 券のコミットのジョブのファイルから計画の指紋を作り直し、券と合わなければ断る（写し間違い・書き換え）。同じ名前の回が別の券か、券を使わずに作った回なら断る
   （名前を替えた券を作り直してもらう）
4. 新しい回なら、回のフォルダに `ticket.txt` を置き、券のコミットを `src/` に出す（git の一時の index で。`/workspace` の作業ツリー・index・今のブランチには触らない）
5. `src/` の `night-main.ts` の `enqueue` を流す。計画（`plan.json`。区切りの決め方は今までと同じ）を作り、回の task を組 `svwb` の後ろに積む:
   - `組み立て`（`prepare`）: `node_modules` を用意し（`package-lock.json` が `/workspace` と同じなら `/workspace` のものを指し、違えば `src/` で `npm ci`。
     組み立てのたびに確かめ直し、止まっている間に `/workspace` の依存が変わっていたら、指すのをやめて `npm ci`）、`src/` で svwb を組み立てて
     （ビルド結果の置き場は `/workspace/rust/target`。コンテナではボリューム）`bin/svwb` に写し、設定の書き間違いを確かめる。済んだら `bin/ready`
   - 区切りごとに 1 つ（`chunk <区切り>`）。同じジョブの区切りは、前の区切りが済むのを待つ（pueue の `--after`）。ジョブの最初の区切りは、組み立てと、
     そのジョブが読むファイルを作る前のジョブの区切り（pick は、線を見る compare）を待つ。`@run:<前の回>` を読む回は、前の回の task がキューに残っていれば、組み立てがそれを待つ
   - `まとめ`（`wrap <回の名前>`）: 回の最後。何も待たない（前の task が失敗しても流れる）。中身は「止まったときのまとめ」と同じ
6. 同じ券・回の名前でもう一度 `add` すると、キューに残っている task（これから回る・回っている・止めてある・中断した）はそのまま使い、無い区切りだけを後ろに積み足す
   （積み足したら、まとめを後ろに付け直す）。2 回流しても増えない

task の名前は `<回の名前> <役目> <書き添え>`（役目は `組み立て`・区切りの番号 `1-2`・`まとめ`）。キューの task は番号ではなく名前で見分ける
（pueue の番号は `pueue clean` の後に使い回される）。task のコマンドは `node <src の night-main.ts> <役目のコマンド> … --root <回の置き場所>` の 1 行で、
作業フォルダは回のフォルダの `src/`（回すのは券のコミットのコード。回している間に `/workspace` のブランチが替わっても同じ）。どこまで済んだかは今までどおり回のフォルダの印（`done/`）で決め、区切りの task は印があれば何もしない。
pueue の状態が消えても（`~/svwb-data/pueue` を消した等）、`add <回の名前>` で続きから積み直せる。
台帳の行のコミットとブランチは券のもの（`SVWB_COMMIT`・`SVWB_BRANCH`）、台帳の行をコミットするのは `/workspace` の git（`plan.json` の `gitDir`）。
`/workspace` のチェックアウトに要るのは `add` があることだけ（このしくみが入る前のチェックアウトなら、ホストで `git pull` を 1 回）。

**`start`・`pause`**:

- `start`: 中断した task（電源が切れた等）を同じ番号のまま積み直し（`pueue restart --in-place`。後ろの task がそれを待っている）、前の止める時刻をやめて、
  `--until` を付けたときだけ止める時刻の task（組 `svwb-ctl` に、その時刻に `pueue pause --group svwb` を流す task）を置き、組を回す。
  昼かは聞かない（いつ回すかはユーザーが決める。2026-11-24 から。前は昼に 1 回聞き、既定で朝 7 時に止めていた）
- 止める時刻と `pause` は pueue の一時停止: 回していた区切りの svwb を止め（SIGSTOP）、次の `start` で続ける（SIGCONT）。区切りを失わない。
  止める時刻の前に次の区切りが済むかは見ない。凍っている間も svwb はメモリを持ったまま（CPU は使わない）
- `pause --wait`: 回している区切りが済んでから止まる（凍らせない）

**止まり方**（区切りの印・印が無いときの作り直し・入力が無いときの失敗は上の「止まり方と再開」）:

| こと | どうなるか |
| --- | --- |
| 止める時刻・`pause` | 回していた区切りは凍る（失わない）。`status` は「一時停止している（… queue.sh start で続きから）」 |
| 電源が切れた・コンテナが止まった | 立ち上がり直した pueue は、回していた task を中断（Killed）にし、組を止めたままにする。`status` は「中断した N 区切り」。次の `start` がその区切りを最初から回し直す |
| `pueued` だけが落ちた | `compose.yaml` が 10 秒後に立て直す。回していた区切りは動き続けていることがあるので、区切りの task は lock（`chunks/<区切り>.lock`）を取り、前のものが終わるのを待つ（済んでいれば何もしない） |
| 区切りが失敗した | そのジョブの後ろの区切りと、それを待つ task は回らない（pueue の DependencyFailed）。ほかのジョブ・ほかの回は回る。`status` は「積んでいない N 区切り」。直したら `add <回の名前>` |
| 組み立てが失敗した | その回の区切りは回らない。`status` は「組み立てが失敗した（pueue log <番号>）」 |
| `remove <回の名前>` | その回のまだ回していない task（と中断した task）をキューから外す。回のフォルダと済んだ区切りは残る。積み直すなら `add <回の名前>` |

`queue-push.sh`（`wrap --pending`）は、区切りが凍っている回も、済んだ区切りの分をまとめる（区切りを回している最中の回はまとめない）。
続きが済むと、その回の最後の task が残りの区切りの行をまとめ直す（`night/<回の名前>` に次のコミット）。

**確かめたこと**（2026-11-23、クラウド環境）:

## 止まったときのまとめ（決めたこと、2026-11-19）

ユーザーの希望（AI がその場で作るコマンドの承認を無くし、エンジニアでなくても回せるくらい単純にする）で、朝に打つコマンドを無くした。

回の最後の task（まとめ。区切りが失敗しても流れる）が、次の 2 つをする（`scripts/night-main.ts` の `wrapUp`）。
どちらかが失敗しても、もう一方はする。結果は `night.log` と `status` に出る。
途中で止まっている回（一時停止・止める時刻・電源が切れた）と、まとめている途中で落ちた回は、`status` に「まとめ: まだ」と出て、
`queue-push.sh` が push の前に済んだ区切りの分をまとめる（`wrap --pending`。手でなら `wrap <名前>`）。
拾うのは、2026-11-19 からの版で作った回だけ（`session.json` の `wraps`。キューの回にはいつも付く）。それより前の版で回した回は、名前を渡した `wrap <名前>` のときだけまとめる

1. **台帳の行のコミット**: ジョブごとに 1 行にまとめた行（`queueRows`）を、ブランチ `night/<回の名前>` の
   `docs/ledger.jsonl` の末尾に足してコミットする。ブランチが無ければ回のコミットから作り、あれば先に積む。git の低い層のコマンドで

     まとめた行は、同じ試合番号を 1 回で回したときと同じ勝ち数・組の数・誤差になる（組の勝率のばらつきから出し直す。クラウド環境で確かめた）。

   - 足すのは、ブランチの台帳がまだ覆っていない区切りの行だけ（`coveredChunks`）。止まった回の続きを回した後は、残りの区切りの行が次のコミットになる

   - 行とメッセージの中の回のフォルダの道は、回の名前からの道（`@<回の名前>/…`）にする（`portablePath`。PC の中の道を公開するブランチに載せない。2026-11-19 から。
     前の行は書き換えない）。メッセージの出口の場所は `~/svwb-data/outbox/<回の名前>`（ホストでも同じ場所）
   - 名前とメールはいつも「svwb queue <queue@svwb.invalid>」（2026-11-24 まで「svwb night queue <night-queue@svwb.invalid>」。git の設定や `.env` のものは使わない。ブランチは公開されるので、メールを載せない。

   - まとめるたびに作り直す（前のものと入れ替える）。途中は `~/svwb-data/outbox/.<名前>.tmp/` に書くので、作りかけを上げることはない

**結果を上げる（ユーザー）**: ホストで `~/Shadowverse-Wb-Sim/docker/remote-control/queue-push.sh`。何度流してもよい。コンテナには GitHub の認証情報が無いので、push はホストで。
するのは次の 3 つ。

1. まとめが済んでいない回（電源が切れた回など）があれば、コンテナの中でまとめる（`npm run queue -- wrap --pending`。コンテナが動いていなければ飛ばす）
2. まだ上げていない `night/` のブランチを push する
3. **片付け**: その回の行が 1 つ以上あり、全部が GitHub の main の台帳にそのままある（スレッドが取り込み、PR がマージされた）回のブランチは、上げ直さず、
   GitHub に残っていれば消す。手元のブランチは残す（止まった回の続きを回すと、その上に積む。積んだ行は main に無いので、また上がる）。
   GitHub で手で消しても、上げ直さない

**スレッド**:

- `npm run queue -- ingest <回の名前>`: `git fetch` でブランチを `refs/night/<回の名前>` に取ってきて、その回の行（`queue` が回の名前）のうち、
  作業ブランチの台帳にまだ無いもの（同じ回・種類・名前・コミットで試合番号が重なる行があれば足さない）を末尾に足す。足した行の表と、
  ブランチの最後のコミットのメッセージ（PC で見た結果）を出す。台帳のコミットと push はスレッドがする（今までどおり作業ブランチに）。2 回流しても同じ行は足さない
- `npm run queue -- ingest <上がったファイル…>`: 出口のアーカイブを確かめて共有フォルダに展開する（ファイルごとに `outbox.json` の sha256 と比べ、
  合ったものだけを置く。同じ中身は書き直さない。同じ回の新しいまとめが共有フォルダにあれば、古いまとめでは置き換えない）。足りないアーカイブ・壊れたアーカイブは
  名前を出して 1 で終わる（上げ直して、もう一度流す）。置くのはその回の `data/selfplay/<名前>/`・`data/models/<名前>/`・`data/kifu/<名前>/`・`logs/<名前>/` の下だけ
  （一覧にあっても、ほかの場所の道は「置けない場所」として置かない）。台帳の行は足さない（行はブランチから）
- 確かめたこと（2026-11-19）: 偽物の svwb で、途中で止めた回と続きを回した回のそれぞれでまとめを作り、ブランチから `ingest` した台帳の行が、
  同じところで前のやり方の `finish`（朝に台帳に足していたもの。2026-11-25 に外した）を流したときの行と 1 文字も違わないこと。
  クラウド環境で本物の svwb の小さいキュー（compare 24 組・misses 2 回・survey 4 試合）でも、3 回のまとめのブランチから `ingest` した 4 行が `finish` の 4 行と同じだった。
  初めは survey の行の `at`（survey report を流した時刻）だけが違ったので、まとめが作った survey の行（`survey-<番号>-ledger.jsonl`。
  その後に調査の結果が書き足されていなければ）を使い回すようにした

## 長い回（自己対戦・学習）を区切れるか（2026-11-10 に調べた）

2026-11-13 に、上の「学び直しの流れ」のジョブとしてキューに入れた（自己対戦は 3000 試合ずつのファイル、学習は 1 つのジョブ）。以下はその前に調べたこと。

- **`td selfplay`**: コマンドの中には再開の仕組みが無い（`--out` を最初から書き直し、終わった順に書く）。ただし試合は番号（`--start` から）とモデルで決まるので、
  番号の範囲で分けて別のファイルに書けば、1 回で回したのと同じ試合の集まりになる（6 試合を 1 回と 3＋3 で回し、行を並べ替えると一致した）。
  `relearn.sh` は `CHUNK` 試合ごとに `s<i>.jsonl.gz` に残して済んだファイルを飛ばすので、もう区切って再開できる。
  PC で `CHUNK=3000`（介入の試合を含む）が 13〜16 分（relearn9 の `relearn-t.log`）なので、`CHUNK=1500` にすれば 1 区切り 7 分ほど
- **`td train`**: 再開できない。学んだ重みは最後にだけ書き、途中の状態（エポックごとの重み・乱数・一番良かったエポック）を残さない。
  `--seed` が同じなら最初からやり直して同じモデルになる。PC で 60000 試合・3 エポックが 27 分（relearn9 の `t-train.log`、1646 秒）。
  エポックの終わりに重みと乱数を書き出せば、エポックの切れ目（9 分ほどごと）から再開できる（直すかは決めていない）
- **`relearn.sh` のほかの段**（間引き・埋め・見込みのデータ・見込みの学習・比べ）: 段ごとに出力のファイルがあれば飛ばすので、段の切れ目から再開できる。
  比べ（compare・yardstick）は 1 段が数分〜十数分
- キューに入れるなら、ジョブの種類に「シェルのジョブ」（`CLOUD_W` を渡して流し、止める時刻には止めて、次の夜に流し直す）を足すのが近道。
  止めたときに失うのは、そのとき回していた段（学習なら最大 27 分）
