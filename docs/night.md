# 夜のキュー（`npm run night`）

ユーザーの PC で対戦を回すのは、夜だけ、それもユーザーが「今夜は回す」と決めた夜だけ（昼はゲームがカクつく。夜も電源を切る日がある。2026-11-10）。
そのための道具が夜のキュー。ジョブを並べたファイルを上から順に、5〜10 分の区切りに分けて回し、区切りごとに結果を残す。

- 朝は何も打たない。キューが止まるとき（全部済んだ・止める時刻・失敗・`stop`）に、自分で台帳の行をブランチ `night/<回の名前>` にコミットし、
  棋譜などを出口のフォルダ（`~/svwb-data/outbox/<回の名前>/`）にまとめる。ユーザーはホストで push を 1 つ流すだけ（下の「止まったときのまとめ」。2026-11-19 から）
- 夜に始めるのも 1 行。スレッドが `plan` で出した券（ブランチ・コミット・ジョブのファイル・止める時刻・計画の指紋の 1 行）を、ユーザーがホストで
  `docker/remote-control/night.sh go <券>` で流す（下の「券と go」。2026-11-19 から）
- 始めるのは `go`・`start`・`resume` だけ。PC やコンテナの起動で勝手には始まらない
- 電源が切れても、失うのは回していた区切りだけ。次に回すと決めた夜に同じ券を流す（か `resume`）と続きから回る
- 朝の決めた時刻（既定 07:00、東京）までに次の区切りが終わらない見込みなら、区切りの切れ目で止まる。手で止めるのは `stop`
- 回す本体は、セッションから切り離して立てる（`setsid`）。Remote Control のセッションが終わっても続く
- 本体は `scripts/night-main.ts`（出口のまとめと展開は `scripts/night-outbox.ts`）。テストは `tests/night.test.ts`（svwb の代わりに台帳の行だけを書く偽物で、区切り・再開・止め方・まとめを確かめる）
- 自己対戦から学習・判定までの学び直しの流れも 1 つのキューに並べられる（下の「学び直しの流れ」）

## ユーザーの手順（1 ページ）

ふだん PC で打つのは、夜に始める 1 つと、朝の push の 1 つだけ。どちらもホスト（WSL の Ubuntu）の端末で流す（どのフォルダからでもよい）。
コンテナ（`docker compose up -d`）が動いていること。

1. **夕方**: スレッドが計画の表と、`~/Shadowverse-Wb-Sim/docker/remote-control/night.sh go svwb-night-1 …` で始まる 1 行（券）を見せる。
   回してよければ、スレッドに「今夜は回す」と伝える
2. **夜**: その 1 行をそのまま貼って流す。svwb を組み立て（数分）、設定の書き間違いを確かめてから、切り離して回し始めて戻る（端末は閉じてよい）

   ```sh
   ~/Shadowverse-Wb-Sim/docker/remote-control/night.sh go svwb-night-1 name=… branch=… commit=… jobs=… until=07:00 plan=…
   ```

   昼（7 時〜18 時）に流すと、回してよいかを 1 回聞く（`y` で始める）。同じ 1 行を 2 回流しても、動いていれば「もう動いています」、
   済んでいれば「全部済んでいます」と言うだけ。途中で止まった回（電源が切れた・止める時刻）は、次の夜に同じ 1 行で続きから回る
3. **朝**: キューは止まるときに結果を自分でまとめてある。ホストで次を流し、スレッドに「<回の名前> を push した」と伝える

   ```sh
   ~/Shadowverse-Wb-Sim/docker/remote-control/night-push.sh
   ```

   スレッドが台帳に足し、結果を報告する。様子だけ見たいときは `~/Shadowverse-Wb-Sim/docker/remote-control/night.sh status`、
   夜のうちに止めたいときは `… night.sh stop`（回している区切りが終わったら止まる。`stop --now` ですぐ）
4. **棋譜・モデルなどが要るとき**（スレッドに言われたときだけ）: エクスプローラーで `\\wsl.localhost\Ubuntu\home\<ユーザー名>\svwb-data\outbox\<回の名前>`
   を開き、中のファイルを全部スレッドに上げる（中の `案内.txt` に、ファイルの数と大きさと結果の表がある）。取り込みが済んだら、そのフォルダは消してよい

## 1 晩の流れ

1. **昼（クラウドのスレッド）**: 変更を作業ブランチに push し、ジョブのファイルを書く（下の「ジョブのファイル」。ブランチの `night/` に置いてコミットし、push する）。
   `npm run night -- plan <ファイル> --machine svwb-docker` で PC での見込みと券を出し、表と券の 1 行（`~/Shadowverse-Wb-Sim/docker/remote-control/night.sh go …`）を
   そのまま見せて「今夜これを回してよいか」を 1 回だけ聞く。承認は 1 晩分まとめて取る（CLAUDE.md「実験を回す場所」）。キューの中のジョブを 1 つずつは聞かない。
   券が出ないとき（「券は出していません: …」）は、書いてある理由（コミットしていない・push していない）を直して流し直す
2. **夜（ユーザーが「今夜は回す」と言ったら）**: ユーザーがホストで券の 1 行を流す（下の「券と go」）。前のように PC の Remote Control で
   `npm run night -- start <ファイル> --yes` を流してもよい（新しい道を PC の 1 晩で確かめるまで残す）
3. **朝**: キューは止まるときに、台帳の行をブランチ `night/<回の名前>` にコミットし、棋譜などを出口のフォルダにまとめてある（下の「止まったときのまとめ」）。
   ユーザーがホストで `docker/remote-control/night-push.sh` を流し、スレッドが `npm run night -- ingest <回の名前>` で作業ブランチの台帳に足してコミットする。
   棋譜・モデルなどが要るときだけ、出口のフォルダのファイルを上げてもらい、`npm run night -- ingest <ファイル…>` で共有フォルダに展開する。
   前の `finish --commit` も残してある（新しいやり方を PC の 1 晩で確かめるまで）
4. **途中で止まった回の続き**: 次に回すと決めた夜に、同じ券の 1 行を流す（止める時刻だけ替えた券でもよい。中では `resume`。済んだ区切りを飛ばす）。止まったときにも、続きが済んだときにも
   まとめるので、朝の push とスレッドの ingest はどちらのときも同じ

1 晩に回すキューは 1 つ（動いている回があれば `go`・`start`・`resume` は断る）。1 つのキューは 1 つのコミットで回す。
違う版どうしは、新しい読み方を設定の項目にして既定を切っておけば、同じコミットの compare で比べられる（今までと同じ）。

## コマンド

```sh
npm run night -- plan <ジョブのファイル> [--until 07:00] [--threads N] [--machine 名前] [--chunk-min 7.5] [--tz Asia/Tokyo] [--name 名前]   # 見込みと券
npm run night -- go <券>                                               # コンテナの中で（ホストからは docker/remote-control/night.sh go <券>）
npm run night -- start <ジョブのファイル> --yes [--name 名前] [--until 07:00] [--threads N] [--chunk-min 7.5] [--allow-dirty]
npm run night -- status [名前]
npm run night -- stop [名前] [--now]
npm run night -- resume [名前] --yes [--until 07:00] [--threads N]
npm run night -- finish [名前] [--commit] [--pack] [--ledger 台帳]   # 前の朝のやり方（PC の 1 晩で新しいやり方を確かめるまで残す）
npm run night -- wrap [名前|--pending]                                 # 止まったときのまとめをやり直す（電源が切れた回・まとめが失敗したとき。--pending はまとめていない回を全部）
npm run night -- ingest <回の名前|ファイル…> [--ledger 台帳] [--to /mnt/project-files] [--remote origin]   # スレッドで
npm run night -- list
```

| 引数 | 既定 | 意味 |
| --- | --- | --- |
| `--until` | `07:00` | 止める時刻。`HH:MM` は時刻帯（`--tz`、既定 `Asia/Tokyo`。コンテナの時計は UTC）で次に来るその時刻。`+90m`・`+2h`（今から）や ISO の日時も書ける |
| `--threads N` | そのマシンの全部 | 使うスレッド数（svwb の `THREADS`）。結果は変わらず、速さだけが変わる。`resume` で替えてもよい |
| `--machine 名前` | このマシン | `plan` の見込みに使うマシン（PC は `svwb-docker`）。そのマシンの決めておいたスレッド数も使う |
| `--chunk-min` | 7.5 | 区切りのおよその長さ（分）。見込みから区切りの大きさを決める |
| `--name` | `night-<日付>-<時刻>`（`plan` の券は `night-<日付>`） | 回の名前（フォルダの名前）。`plan` に渡すと券の名前になる |
| `go <券>` | | 券の回を始めるか、続きを回す（下の「券と go」）。`--yes` を付けると昼でも聞かない（端末の無いところで流すとき） |
| `--yes` | なし | 付けないと、計画の表を出すだけで始めない。付けるのは、ユーザーが今夜回すと決めた後だけ |
| `--allow-dirty` | なし | コミットしていない変更があっても始める（試すとき用。ふつうは push してから回す） |
| `stop --now` | なし | 回している区切りをすぐ止める（その区切りは次の `resume` で回し直す）。付けなければ、回している区切りが終わってから止まる |
| `finish --commit` | なし | 足した台帳（`docs/ledger.jsonl`）だけをコミットする。push はしない |
| `ingest <回の名前>` | | スレッドで。GitHub からブランチ `night/<回の名前>`（`night/<回の名前>` と書いてもよい）を取ってきて、その回の行のうち台帳にまだ無いものを足す（`--ledger` の台帳、既定は `docs/ledger.jsonl`）。コミットはスレッドが |
| `ingest <ファイル…>` | | スレッドで。上がった出口のファイル（名前が変わっていてよい。案内は読み飛ばす）を確かめて、`--to`（既定 `/mnt/project-files`）の `data/…/<回の名前>/`・`logs/<回の名前>/` に展開する |
| `finish --pack` | なし | 回のフォルダを `pack-run --only logs,kifu` でまとめる（`~/svwb-upload/<名前>.tar.gz`。共有フォルダに上げる用。棋譜は `data/kifu/<名前>/` に入る） |

回は `~/svwb-data/night/<名前>/` に置く（環境変数 `SVWB_NIGHT_DIR` か `--root` で替えられる）。名前を省くと、`status`・`finish` は最後の回、
`stop` は動いている回、`resume` は済んでいない最後の回を選ぶ。

## ジョブのファイル

1 行 1 ジョブで、svwb のコマンドと同じ形（`compare`・`yardstick`・`profile`・`misses`・`survey`。行の頭の `svwb` は書いても書かなくてもよい）。
学び直しの流れ（自己対戦・学習・後処理）のジョブ（`td selfplay`・`beam-gap`・`td`・`potential`・`pick`）は下の「学び直しの流れ」。
`#` から行の終わりまでは書き添え。上から順に回す。例:

```sh
# 定例（night/routine.txt を先頭に写してもよい）
yardstick --ref strong --opts '{}' --games 4000 --start 0 --label 定例-強い相手
# 補正の入れ替え（1.1 万試合で 1 ポイントを見る）
compare 5600 '{"valueNet":"data/models/x.json"}' '{}' 200000 --label 補正x
profile --games 49
```

- **compare**: `compare <試合数> '<A>' '<B>' [最初の試合番号] [B のデッキ] [--no-mirror] [--decks …] [--with <デッキ名> | --without <デッキ名>] --label 名前`（`npm run compare` と同じ。
  `--with` はそのデッキの絡む組だけ、`--without` は絡まない組だけ。試合番号はその組の k 番目の番号）
- **yardstick**: `yardstick [--ref classic|strong|pool-v0|pool-r3] [--opts '<設定>'] [--games 1000] [--start 0] --label 名前`
- **profile**（速さ）: `profile [--opts '<設定>'] [--games 49] [--start 0] [--rhino] [--decks <デッキ>,…|@<デッキの組>]`。結果は回のフォルダの `speed-<番号>.md`・`.json`（`svwb profile` の報告。`--decks` なら型ごとの表も出る。PP を残して終えたターンの割合などを、学び直しの回ごとに見るのに使う）
- **misses**（見落とし問題集、`docs/misses.md`）: `misses [run] [--opts '<設定>'] [--trials 24] [--seed 1] --label 名前`。分けずに 1 区切りで回す。
  見込みの「1 試合」は、全部の問を 1 回ずつ解く秒（台帳の前の回から、問の数の違いを割り直して見込む）。`--only`・`--dir`・`--out` は使えない（問題集全体を解く）
- **survey**（候補の打ち比べ調査、`docs/survey.md`）: `survey [run] --games a-b [--rate 0.1] [--m 32] [--extra 4] [--confirm 96] [--flag 10] [--batch 8] [--opts '<設定>'] [--decks …] --label 名前`
  （`--games N --start S` でもよい。`--opts`・`--decks` は新しいプールの AI とデッキで打つ用。2026-11-16 から）。試合番号の範囲で区切り、どの区切りも回のフォルダの `survey-<番号>.jsonl` に足す（1 つの番号で 1 試合。
  見込みの「1 試合」は、その試合から取った局面の打ち比べを含む秒）。区切りごとの台帳の行は無く、ジョブの区切りが全部済んだ後の `finish` が
  `svwb survey report` で 1 行を足す（報告は `survey-<番号>.md`、問題集に足す候補の局面は `survey-<番号>-states/`）。`--out` は使えない
- `--label` は compare・yardstick・misses・survey に要る（区切りの結果を後で足し合わせ、台帳を引くため）。比べの案ごとに付ける
- 試合番号（シード）の範囲は、前の回と重ならないように選ぶ（同じ試合を 2 回数えない。`npm run ledger -- runs --grep <名前>` で前の範囲を見る）
- キューでは使えない引数: `--no-ledger`（結果は台帳から集める）・`--kifu`・`--replays`・`--no-kifu`（棋譜はキューが回のフォルダの `kifu/` に書く。下の「回のフォルダ」）・`yardstick --record`
  （物差しの表に足すのは、終わった後に足し合わせた数字で）・`profile --json/--report/--baseline/--record`（キューが回のフォルダに書く）
- `--est <秒>`: 1 試合の見込みの秒（回すマシン・スレッド数で）。キューだけが読む。読み方を大きく変える設定（深い読み等）で、台帳にまだ回が無いときに。
  `td`・`potential` は全体の秒

### 学び直しの流れ（2026-11-13）

自己対戦から学習・後処理・判定の compare までを 1 つのキューに並べる（例は `night/relearn-b.txt`、小さく試すのは `night/relearn-b-small.txt`）。
ファイルは回のフォルダに作り、ジョブの行では `@/` と書く（`@/s-3.jsonl.gz` 等。設定の JSON の中にも書ける）。`{1..20}` は `1,2,…,20` のカンマ区切りに開く
（`--data @/s-{1..20}.jsonl.gz`）。

- **td selfplay**: `td selfplay --games N [--start S] --chunk C --out @/s-{k}.jsonl.gz --est <1 試合の秒> [ほかの引数]`。C 試合ずつ（大きさはそろえる）の区切りで、
  `{k}` に区切りの番号（1 から）を入れたファイルに書く。`.gz` なら書き終えた後にキューが gzip する。区切りの大きさは時間でなく `--chunk` で決める（後のジョブがファイルの名前で読むので）
- **beam-gap**（見込みの学びのデータ）: `beam-gap --games N --from S --chunk C --inputs @/pot-{k}.jsonl [--out @/pot-{k}-rows.jsonl] --est … [ほかの引数]`。区切り方は td selfplay と同じ
- **td**・**potential**（TypeScript の学習。`npm run td`・`npm run potential` と同じ引数）: `td train … --out @/n.json --est <全体の秒>`。1 つのジョブが 1 区切りで、
  `--out` のファイルを作る。途中では止められない（止める時刻に 15 分を足しても終わらなければ止め、次は最初から）ので、`--est` を多めに書く。
  `start` のときにスクリプトをビルドして回のフォルダの `bin/td/`・`bin/potential/` に置き、それを回す（夜の間にチェックアウトが替わっても同じコード）
  `td train`・`td prune` の行は、Rust 版（`svwb td train`・`prune`。同じモデルを書き、速くてメモリが少ない。[commands.md](commands.md)「svwb」）を
  回のフォルダに写した svwb で回す（2026-11-15 から既定。B の 6 万試合で TypeScript 版と同じモデルになるのを確かめた）。実験用の引数（`--attr` 等）を使う行は
  `--impl ts` を付けて TypeScript 版で回す（Rust 版はその引数をエラーにする）。2026-11-14 までの行（`night/relearn-b.txt` 等）は、`--impl` が無ければ TypeScript 版で回したもの。
  `--est` は TypeScript 版の時間のままの行が多い（多めに見積もる分には困らない）。PC の Rust 版の実測は、段階 4 の R1（新しいプールの自己対戦 6 万試合、入力あり）で
  学習 14 分・間引き 24 秒（`night/pool-r2.txt` の `--est` はこれから）
- **pick**: `pick --compare <前の compare の台帳の名前> --pass <ファイル> --fail <ファイル> --out <ファイル>`。その compare の済んだ区切りをまとめ、
  A の勝率 − 50% − 2 SE が 0 より大きければ `--pass`、そうでなければ `--fail` のファイルを `--out` に写す（回す前に決めた線で、後のジョブの設定を選ぶ）。
  結果は回のフォルダの `pick-<番号>.json` と、`status`・`finish` の表
- 作るファイル（td selfplay・beam-gap は区切りのファイル、td・potential・pick は `--out`）は、途中は `.tmp` に書き、済んでから名前を替える。
  ファイルがあれば、印が無くても済んだものとする（手でファイルを置けば、そのジョブを飛ばせる）
- `@/` のファイルは前のジョブが作るものだけを読める（ジョブのファイルを読むときに確かめる）。回すときに前のジョブが作るはずのファイルが無ければ
  （失敗した・まだ済んでいない）、そのジョブを回さずに失敗にする。`resume` で、失敗したジョブから続きを回す
- `start` の確かめでは、`@/` のモデルを今の既定（`valueNet` は `data/value-net.json`、`potentialNet` は `data/potential-net.json`）にして設定を読み、
  td selfplay・beam-gap は 0 試合で回す。td・potential・pick の引数は確かめない（小さく試してから PC に回す）

## 見積もりと区切り

1 試合の秒を、次の順に見積もる。

1. `--est`
2. 台帳（`docs/ledger.jsonl`）の、同じ比べ（種類・両方の設定・絞り込み・鏡・相手）・同じマシンの最近の 5 回。同じスレッド数の回があればその速さ、
   無ければスレッド秒（1 試合の秒 × スレッド数）で割り直す。夜のキューの回もマシン（`svwb-docker`）とスレッド数を台帳に書くので、回すほど当たる
3. 決めておいた値（`scripts/night-main.ts` の `SPEEDS`。PC は compare 3200 試合 5 分ほど・物差しは `docs/yardstick.md` の「（PC）」の行から、
   クラウド環境は 2026-11-10 に測った値。どれも今の既定どうし。設定が違えば「設定の違いは見ていない」と出る。
   survey は 2026-11-11 にクラウド環境で小さく試した値（`docs/survey.md`「速さ」）で、局面の割合（`--rate`）にだけ比べる）

区切りの大きさは、見込みで `--chunk-min` 分ほどになる組の数（大きさはそろえる）。区切りは `start` のときに決めて `plan.json` に書き、
`resume` でも同じ区切りを使う。回の途中では、そのジョブで済んだ区切りの速さで次の区切りの長さを見込む。

| こと | どうなるか |
| --- | --- |
| 区切りが済んだ | 台帳の行（回のフォルダの `ledger.jsonl`）を書いた後、`done/<区切り>.json` の印を書く（どちらも fsync） |
| 止める時刻 | 区切りを始める前に、「今 + その区切りの見込み」が止める時刻を過ぎるなら止まる。見込みが外れて止める時刻を 15 分過ぎても終わらない区切りは止める（その区切りは失う） |
| `stop` | 回している区切りが終わったら止まる（`STOP` を置く。`resume` で消える） |
| `stop --now` | 回している区切りを止める（その区切りは失う） |
| 電源が切れた・コンテナが止まった | 回していた区切りを失う。`status` は「止まっている（電源が切れたか、途中で落ちた）」。`resume` で続きから |
| 台帳の行を書いた直後に電源が切れた（印が無い） | `resume` で、台帳に同じ引数の行があれば回さずに印を作る（survey は、出力に区切りの試合が全部あれば） |
| survey の区切りが途中で止まった | 書いた試合（`--batch` 試合ごとに書く）は残る。`resume` で回し直すと、出力に既にある試合を飛ばして続きから |
| 区切りが失敗した（svwb が 0 以外で終わった） | そのジョブの残りを飛ばし、次のジョブへ。`status` の「メモ」に出る。`resume` でやり直す |
| 作るファイルができた直後に電源が切れた（印が無い） | `resume` で、作るファイルがあれば回さずに印を作る（学び直しの流れのジョブ） |
| 前のジョブが作るファイルが無い | そのジョブを回さずに失敗にする（「入力がありません」）。前のジョブを `resume` でやり直せば、続けて回る |

- 回すのは `start` のときに回のフォルダに写した svwb（`bin/svwb`）。夜の間にほかのセッションが同じ `/workspace` で組み立て直しても、
  `resume` が次の夜でも、同じコードで回る。台帳の行のコミットとブランチも `start` のときのもの（`SVWB_COMMIT`・`SVWB_BRANCH`）
- 設定の中のファイル（`"valueNet":"…json"` 等）は、回すたびにリポジトリから読む。夜の間はそのファイルを替えない（台帳の `files` に中身の指紋が残る）
- コンテナ（`docker/remote-control`）が止まると、中のキューも止まる。`compose.yaml` は、`claude remote-control` が終わっても（ネットワークが切れた等）
  コンテナを止めずに中で立ち上げ直す形にしてある（2026-11-10。前の形では、`claude` が終わるとコンテナごと立ち上げ直り、キューが止まった）。

## 券と go（決めたこと、2026-11-19）

ユーザーの希望で、夜に始めるのも、ホストで 1 行を流すだけにした。ユーザーの決定: Windows のショートカットではなく、`docker compose exec` で流す
.sh か npm のコマンドにする（`docker/remote-control/night.sh`。中身は `docker compose exec rc npm run -s night -- <引数>`）。

**券**は 1 行で、`svwb-night-1 name=<回の名前> branch=<ブランチ> commit=<sha の頭 12 桁> jobs=<ジョブのファイル> until=<止める時刻> plan=<計画の指紋>`
（`tz`・`threads`・`chunk` は `plan` に渡したときだけ入る）。計画の指紋は、ほかの項目とジョブのファイルの中身の sha256 の頭 12 桁。
`plan` は、ジョブのファイルをコミットしてあり、コミットしていない変更が無く、今のコミットを `origin/<ブランチ>` に push してあるときだけ券を出す。

`go <券>`（コンテナの中で。`/workspace` のチェックアウトの `night-main.ts` が流れる）がすること:

1. 券を読む。1 語目が違う形（`svwb-night-2` など）なら、ホストで `git pull` してから流すように言う
2. 券のコミットが `/workspace` の git に無ければ、GitHub から券のブランチを取ってくる（リポジトリは公開なので https で。コンテナに認証情報は要らない。
   `origin` が `git@github.com:…` でも https の形に直して取る）。取ってきても無ければ断る
3. 券のコミットのジョブのファイルから計画の指紋を作り直し、券と合わなければ断る（写し間違い・書き換え）
4. 同じ名前の回があれば: 券を使わずに作った回か、ブランチ・コミット・ジョブのファイル・`chunk` が違う券の回なら断る（名前を替えた券を作り直してもらう）。
   動いていれば「もう動いています」、全部済んでいれば「全部済んでいます」と言って終わる（2 回流しても困らない）
5. ほかの回が動いていれば断る。昼（7 時〜18 時、券の時刻帯）なら 1 回聞く（端末が無ければ断る。`--yes` で聞かない）
6. 新しい回なら、回のフォルダに `ticket.txt` を置き、券のコミットを `src/` に出す（git の一時の index で。`/workspace` の作業ツリー・index・今のブランチには触らない）。
   `node_modules` は、`package-lock.json` が `/workspace` と同じなら `/workspace` のものを指し、違えば `src/` で `npm ci`。
   途中の回の `go` でも確かめ直す（止まっている間に `/workspace` の依存が変わっていたら、指すのをやめて `npm ci`）
7. `src/` の `night-main.ts` の `start`（新しい回）か `resume`（途中の回）を流す。svwb は `src/` で組み立てる（ビルド結果の置き場は `/workspace/rust/target`。
   コンテナではボリューム）。台帳の行のコミットとブランチは券のもの（`SVWB_COMMIT`・`SVWB_BRANCH`）、台帳の行をコミットするのは `/workspace` の git（`plan.json` の `gitDir`）

回すのは券のコミットのコード（`src/`）なので、夜の間にほかのスレッドが `/workspace` のブランチを替えても、次の夜に続きを回しても同じ。
`/workspace` のチェックアウトに要るのは `go` があることだけ（このしくみが入る前のチェックアウトなら、ホストで `git pull` を 1 回）。

## 止まったときのまとめ（決めたこと、2026-11-19）

ユーザーの希望（AI がその場で作るコマンドの承認を無くし、エンジニアでなくても回せるくらい単純にする）で、朝に打つコマンドを無くした。
ユーザーの決定: 結果は、PC で台帳の行をブランチにコミットしてホストで push する形で渡す（大きいファイルは出口に置き、要るときだけ上げる）。

worker は止まるとき（全部済んだ・止める時刻・失敗・`stop`・`stop --now`）に、次の 2 つをしてから終わる（`scripts/night-main.ts` の `wrapUp`）。
どちらかが失敗しても、もう一方はする。結果は `night.log` と `status` に出る。
電源が切れた回と、まとめている途中で落ちた回は、`status` に「まとめ: まだ」と出て、朝の `night-push.sh` が push の前にまとめる（`wrap --pending`。手でなら `wrap <名前>`）。
拾うのは、この版（2026-11-19 から）で `start`・`resume` した回だけ（`session.json` の `wraps`）。前の版で回した回は、名前を渡した `wrap <名前>` のときだけまとめる
（`~/svwb-data/night/` に残っている前の回を、朝に全部まとめ直して上げないように）。

1. **台帳の行のコミット**: ジョブごとに 1 行にまとめた行（`finish` と同じ作り方。同じ関数 `queueRows`）を、ブランチ `night/<回の名前>` の
   `docs/ledger.jsonl` の末尾に足してコミットする。ブランチが無ければ回のコミットから作り、あれば先に積む。git の低い層のコマンドで
   コミットを作るので、`/workspace` の作業ツリー・index・今のブランチには触らない（夜の間にほかのスレッドが同じ `/workspace` で作業していてもよい）。
   - 足すのは、ブランチの台帳がまだ覆っていない区切りの行だけ（`coveredChunks`。`finish` の `merged.json` と同じ働き）。止まった回の続きを回した後は、
     残りの区切りの行が次のコミットになる（`finish` を 2 回流したときと同じ行）
   - 行が無くてもコミットする（失敗で止まった等も、スレッドがメッセージで分かるように）。メッセージは 1 行目が `台帳: 夜のキュー <名前> の結果（N 行、<コミット>）`、
     その下に出口の場所と、`status` と同じ表と、この回の済んだ区切りを全部まとめた表。`wrap` を流し直しても、足す行も様子の違いも無ければコミットしない
   - 行とメッセージの中の回のフォルダの道は、回の名前からの道（`@<回の名前>/…`）にする（`portablePath`。PC の中の道を公開するブランチに載せない。2026-11-19 から。
     前の行は書き換えない）。メッセージの出口の場所は `~/svwb-data/outbox/<回の名前>`（ホストでも同じ場所）
   - 名前とメールはいつも「svwb night queue <night-queue@svwb.invalid>」（git の設定や `.env` のものは使わない。ブランチは公開されるので、メールを載せない。
     このコミットは行を運ぶためだけのもので、main には入らない）
2. **出口のフォルダ**: 回のフォルダの 1 段目のファイル（計画・ログ・区切りごとの台帳の行・速さの報告・調査の結果・pick の結果・学び直しのデータとモデル）、
   `kifu/`（棋譜）、`chunks/`（区切りごとの svwb の出力。失敗した区切りの `.log.tmp` も）、`survey-<番号>-states/`（問題集に足す候補の局面）を、
   `~/svwb-data/outbox/<回の名前>/` に `.tar.gz` でまとめる（300MB ごとに分ける。`SVWB_OUTBOX_MAX_MB` で替えられる）。中は pack-run と同じ形
   （`data/selfplay/<名前>/`・`data/models/<名前>/`・`data/kifu/<名前>/`・`logs/<名前>/`）。入れないのは `bin/`・`done/`・`worker.pid`・`STOP`・書きかけ。
   - どのアーカイブにも先頭に `logs/<名前>/outbox.json`（全部のファイルの置き場所・何個目・sha256 と、様子と結果の表）と `MANIFEST.md` が入る。
     同じフォルダの `案内.txt` に、上げるファイルの数と大きさと結果の表を書く
   - 止まるたびに作り直す（前のものと入れ替える）。途中は `~/svwb-data/outbox/.<名前>.tmp/` に書くので、作りかけを上げることはない

**朝（ユーザー）**: ホストで `~/Shadowverse-Wb-Sim/docker/remote-control/night-push.sh`。何度流してもよい。コンテナには GitHub の認証情報が無いので、push はホストで。
するのは次の 3 つ。

1. まとめが済んでいない回（電源が切れた回など）があれば、コンテナの中でまとめる（`npm run night -- wrap --pending`。コンテナが動いていなければ飛ばす）
2. まだ上げていない `night/` のブランチを push する
3. **片付け**: その回の行が 1 つ以上あり、全部が GitHub の main の台帳にそのままある（スレッドが取り込み、PR がマージされた）回のブランチは、上げ直さず、
   GitHub に残っていれば消す。手元のブランチは残す（止まった回の続きを回すと、その上に積む。積んだ行は main に無いので、また上がる）。
   GitHub で手で消しても、上げ直さない

**スレッド**:

- `npm run night -- ingest <回の名前>`: `git fetch` でブランチを `refs/night/<回の名前>` に取ってきて、その回の行（`queue` が回の名前）のうち、
  作業ブランチの台帳にまだ無いもの（同じ回・種類・名前・コミットで試合番号が重なる行があれば足さない）を末尾に足す。足した行の表と、
  ブランチの最後のコミットのメッセージ（PC で見た結果）を出す。台帳のコミットと push はスレッドがする（今までどおり作業ブランチに）。2 回流しても同じ行は足さない
- `npm run night -- ingest <上がったファイル…>`: 出口のアーカイブを確かめて共有フォルダに展開する（ファイルごとに `outbox.json` の sha256 と比べ、
  合ったものだけを置く。同じ中身は書き直さない。同じ回の新しいまとめが共有フォルダにあれば、古いまとめでは置き換えない）。足りないアーカイブ・壊れたアーカイブは
  名前を出して 1 で終わる（上げ直して、もう一度流す）。置くのはその回の `data/selfplay/<名前>/`・`data/models/<名前>/`・`data/kifu/<名前>/`・`logs/<名前>/` の下だけ
  （一覧にあっても、ほかの場所の道は「置けない場所」として置かない）。台帳の行は足さない（行はブランチから）
- 確かめたこと: 偽物の svwb で、途中で止めた回と続きを回した回のそれぞれで止まったときのまとめを作り、ブランチから `ingest` した台帳の行が、
  同じところで `finish` を流したときの行と 1 文字も違わないこと（`tests/night.test.ts`）。
  クラウド環境で本物の svwb の小さいキュー（compare 24 組・misses 2 回・survey 4 試合）を、compare の途中と survey の途中で止めて続きを回し、
  3 回のまとめのブランチから `ingest` した 4 行が、それぞれの止まったところで `finish` を流した 4 行と 1 文字も違わないこと（2026-11-19）。

  （`survey-<番号>-ledger.jsonl`。その後に調査の結果が書き足されていなければ）を使うようにした。PC の 1 晩ではまだ確かめていない

## 台帳の行のコミット（決めたこと、2026-11-10。2026-11-19 から上の「止まったときのまとめ」に替えた。`finish` は PC で確かめるまで残す）

- キューは commit も push もしない。夜の間は、回のフォルダの `ledger.jsonl` にだけ書く（リポジトリの台帳を夜の間に触らないので、
  同じ `/workspace` でほかのスレッドが作業しても混ざらない）
- 朝の `finish` が、ジョブの済んだ区切りを、試合番号の続いたまとまりごとに 1 行にまとめて、リポジトリの台帳（`docs/ledger.jsonl`）に足す（misses は区切りの行に `queue`・`chunks` を足してそのまま写す）。
  まとめた行は、同じ試合番号を 1 回で回したときと同じ勝ち数・組の数・誤差になる（組の勝率のばらつきから出し直す。クラウド環境で確かめた）。
  survey は、ジョブの区切りが全部済んでから `svwb survey report` の行に `queue`・`chunks` を足して 1 行（途中なら `finish` の表の下に「まだ途中」と出る）。
  `queue`（回の名前）と `chunks`（区切りの数）が付き、`cmd` は 1 回で回すときのコマンド。区切りごとの行は回のフォルダに残る
- 2 回 `finish` しても、同じ区切りは 2 回足さない（`merged.json`）。途中で止まった回は、済んだ分だけ足し、続きを回した後の `finish` で残りを足す
- `--commit` で `docs/ledger.jsonl` だけを、チェックアウトしているブランチにコミットする（ふつうはキューのブランチ。違えば `finish` の表に出るコミットで見分ける）。
  コンテナには GitHub の認証情報が無いので、push はユーザーがホストで（`git push`）
- コミットには git の名前とメールが要る。コンテナでは `docker/remote-control/.env` に `GIT_AUTHOR_NAME`・`GIT_AUTHOR_EMAIL`・`GIT_COMMITTER_NAME`・
  `GIT_COMMITTER_EMAIL` を書き、ホストで `docker compose up -d` を流しておく（2026-11-11 の初めての試しでは入っていなかった）。
  `finish --commit` は台帳に足す前にこれを確かめ、決まらなければ何も足さずに止まる。足した後でコミットが失敗したときは、直して `finish --commit` を
  流し直せば、前に足したこの回の行をコミットする
- push されるまでは、`finish` が出す表（`summary.md`）の数字をスレッドに貼って使う。採否を決めるとき（`npm run ledger -- decide --from-label`）は、
  push された台帳から引き直す

## 定例（`night/routine.txt`）

物差し 2 つと速さと見落とし問題集を測るジョブのファイル。既定を変えた後の夜に、キューの先頭に置く（毎晩でなくてよい）。PC で 20 分ほど。

- 弱い相手の物差し `yardstick --ref classic` と強い相手の物差し `--ref strong` を、それぞれ g0〜3999（8000 試合。誤差 0.4〜0.5 ポイントほど）。
  台帳の名前は `定例-弱い相手`・`定例-強い相手`。前に物差しの表に足した g0〜999 の試合を含む
- 速さ `profile --games 49`（`docs/profile.md` と同じ 98 試合）
- 見落とし問題集 `misses --trials 24 --seed 1`（台帳の名前は `定例-見落とし問題集`。PC で 1 分かからない）
- 結果は `npm run ledger -- runs --label 定例`・`npm run ledger -- misses --label 定例` で引き、`docs/STATE.md` の「追う数字」を直す。物差しの表（`docs/yardstick.md`）に足すのは、採用した版だけ（今までどおり）

## 長い回（自己対戦・学習）を区切れるか（2026-11-10 に調べた）

2026-11-13 に、上の「学び直しの流れ」のジョブとしてキューに入れた（自己対戦は 3000 試合ずつのファイル、学習は 1 つのジョブ）。以下はその前に調べたこと。

- **`td selfplay`**: コマンドの中には再開の仕組みが無い（`--out` を最初から書き直し、終わった順に書く）。ただし試合は番号（`--start` から）とモデルで決まるので、
  番号の範囲で分けて別のファイルに書けば、1 回で回したのと同じ試合の集まりになる（6 試合を 1 回と 3＋3 で回し、行を並べ替えると一致した）。
  `relearn.sh` は `CHUNK` 試合ごとに `s<i>.jsonl.gz` に残して済んだファイルを飛ばすので、もう区切って再開できる。
  PC で `CHUNK=3000`（介入の試合を含む）が 13〜16 分（relearn9 の `relearn-t.log`）なので、`CHUNK=1500` にすれば 1 区切り 7 分ほど
- **`td train`**: 再開できない。学んだ重みは最後にだけ書き、途中の状態（エポックごとの重み・乱数・一番良かったエポック）を残さない。
  `--seed` が同じなら最初からやり直して同じモデルになる。PC で 60000 試合・3 エポックが 27 分（relearn9 の `t-train.log`、1646 秒）。
  エポックの終わりに重みと乱数を書き出せば、エポックの切れ目（9 分ほどごと）から再開できる（直すかは決めていない）
- **`relearn.sh` のほかの段**（間引き・埋め・見込みのデータ・見込みの学習・比べ）: 段ごとに出力のファイルがあれば飛ばすので、段の切れ目から再開できる。
  比べ（compare・yardstick）は 1 段が数分〜十数分
- キューに入れるなら、ジョブの種類に「シェルのジョブ」（`CLOUD_W` を渡して流し、止める時刻には止めて、次の夜に流し直す）を足すのが近道。
  止めたときに失うのは、そのとき回していた段（学習なら最大 27 分）
